# CaseLedger Causal Ordering: CaseActor Observation Order Is the Canonical Causal Order

## Context and Problem Statement

`notes/case-ledger-authority.md` states informally that "`log_index` order
*is* causal order", a claim that was confirmed in the native-entry section of
that note and again when `WritePrologueLedgerEntriesNode` was removed
(Issue #1777). `DEMOMA-22-005` relies on the same property, citing ADR-0041
as its basis. ADR-0041 establishes CaseActor-authoritative *initialization*
— it does not establish a normative causal-ordering model.

This leaves DEMOMA-22-005 standing on an unwritten foundation. The property
is real and intended; what is missing is the decision record. Three related
pieces need to be unified as normative requirements:

1. The CaseActor's obligation: `log_index` order is causal order from the
   CaseActor's own perspective.
2. Testable temporal invariants: constraints on `CaseLedgerEntry.published`
   and `log_index` that conformance tests can verify.
3. Participant emission obligations: what a well-behaved participant must do
   to preserve causal fidelity in the assertions it submits to the CaseActor.

## Decision Drivers

- DEMOMA-22-005 requires that invariant tests check declared causal edges
  against observed ledger order, but "observed ledger order is causal order"
  is not itself a normative spec entry.
- The ledger is the replicated source of truth for all participants; the
  ordering model must be unambiguous.
- The CaseActor is a single writer (ADR-0041, CLP-01-003), which uniquely
  positions it to enforce a deterministic ordering model without distributed
  consensus overhead.
- Residual uncertainty about external actor clocks must be explicitly
  acknowledged rather than papered over.

## Considered Options

**A. CaseActor observation order** — the `log_index` sequence assigned by the
CaseActor's single authoritative write path defines causal order. For
internally-generated events, order is known by construction. For inbound
participant assertions, the CaseActor's receipt and commit order is
authoritative. The CaseActor's own `published` timestamp stamps the ledger
envelope; the participant's claimed timestamp is preserved inside the
`payloadSnapshot` but does not determine ledger order.

**B. Vector clock causal tracking** — each activity carries a logical clock
vector across all known participants. The ledger records vector values;
receivers can reconstruct a partial causal order across participants without
routing everything through the CaseActor.

**C. Pure wall-clock ordering** — entries are ordered by their `published`
timestamp alone. Log index is a convenience counter; the authoritative order
is timestamp sort order.

## Decision Outcome

Chosen option: **A, CaseActor observation order**, because:

- The CaseActor is already the single writer (ADR-0041). There is no
  concurrent-write hazard to model.
- Option B requires propagating vector clocks through every wire activity.
  The federated protocol has no guarantee that all participants maintain
  compatible clock vectors, and the complexity cost is not justified when a
  single-writer regime already resolves the ordering problem.
- Option C is unreliable: clock skew between the CaseActor's clock and
  participants' clocks means physically simultaneous events can receive
  arbitrary timestamp order. Timestamps are useful supporting evidence but
  must not be the sole determinant.

### The Ordering Model

The `CaseLedger` is authoritative from the **CaseActor's perspective only**
— a postal cancellation stamp, not a forensic record. The CaseActor records
the sequence in which it observed and processed events. It makes no claim
about when events occurred at other actors.

- For **internal events** generated by the CaseActor itself (e.g., the
  native case-initialization entries in ADR-0041), causal order is known by
  construction: each entry is committed sequentially in a single execution
  path, so the resulting `log_index` sequence is the causal sequence.
- For **external events** (inbound participant assertions), the CaseActor's
  receipt and commit order is the authoritative ordering. The CaseActor
  cannot verify causal claims about events it did not observe.

### CaseActor Timestamp Obligation

The CaseActor MUST ensure:

- If event A causally precedes event B (from the CaseActor's perspective),
  then `log_index(B) > log_index(A)`. Gaps in the `log_index` sequence are
  permitted (entries may be sparse); reversal is not.
- The `published` timestamps on consecutive ledger entries MUST be
  monotonically non-decreasing in `log_index` order. An entry stamped later
  in the sequence MUST NOT carry an earlier timestamp than its predecessor.
- Every ledger entry's `published` timestamp MUST be on or after the case's
  own `published` timestamp. A ledger entry cannot predate the case it
  belongs to.

This is **not** a claim that B immediately follows A (gaps are permitted);
only that B cannot appear before A.

### Participant Emission Obligation

Participants MUST emit protocol messages in causal order, with timestamps
that reflect the actual sequence of events. A participant MUST NOT batch
events and emit them in arbitrary order. If A caused B caused C, the
participant MUST send them in that sequence with monotonically non-decreasing
`published` timestamps. A participant that violates this produces a malformed
assertion — that is a protocol violation on the participant's part, not a
CaseActor failure.

### Residual Uncertainty

Even with the participant obligation above, the CaseActor cannot verify
causal claims from external actors. The ledger is authoritative for what the
CaseActor observed; it is **not** a guarantee of real-world causal fidelity
when external actors self-report events. The CaseActor SHOULD reject payload
assertions with timestamps that are implausibly far in the future or past
relative to its own clock, but it cannot eliminate all timestamp spoofing
from a malicious or malfunctioning participant.

### Consequences

- Good: the `log_index` sequence is the unambiguous causal order. Every
  conformance invariant that references causal order can be evaluated against
  `log_index` without clock comparison.
- Good: `notes/case-ledger-authority.md`'s informal claim is now grounded in
  a normative decision record that DEMOMA-22-005 can cite.
- Good: the residual uncertainty about external actor clocks is explicitly
  acknowledged, rather than being an implicit gap in the spec.
- Neutral: participants bear an obligation the CaseActor can only partially
  enforce (timestamp ordering is checkable; causal ordering across opaque
  participant-internal events is not).
- Bad: a participant whose clock is wrong produces a structurally valid but
  temporally misleading assertion. The CaseActor can flag implausible
  timestamps (SHOULD-level) but cannot always determine the ground truth.

## Validation

Conformance tests in `test/ci/invariants/common.py` verify:

- `entry[N].published >= entry[N-1].published` for all consecutive recorded
  entries within a case.
- `entry.published` is non-null for all entries.
- `log_index` values are unique within a case and form a gapless sequence.
- All entries in a case share the same `case_id`.
- No entry's `published` precedes the case's own `published` timestamp.

These are tracked as a separate implementation issue (runtime enforcement via
extension of `_validate_canonical_entry` and conformance tests).
