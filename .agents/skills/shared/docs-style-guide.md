# Vultron Documentation Style Guide

Prose rules for hand-written pages under `docs/`. Consumed by `write-docs`
(when authoring) and `lint-docs` (when auditing), and referenced by
`check-docs-sync`.

Normative anchor: `specs/diataxis-requirements.yaml` **DF-09-001** requires
`docs/` prose to follow this file. Rule IDs below (`SG-nn`) are style-guide
rule identifiers, not spec IDs; each cites the spec entry it implements where
one exists.

This guide rules on one page at a time. Everything above the page — who a page
is addressed to, how much it may assume, where it sits in the nav, and what a
neighbor may repeat — is settled in `notes/site-information-architecture.md`
(ADR-0102, DF-11). Both documents share one reader model: a reader arrives at a
page from search or a deep link, not by reading the nav in order. SG-07, SG-10
through SG-12, SG-40, and SG-44 are the rules that touch that boundary, and each
points at the note rather than restating it.

## Scope

| In scope | Out of scope |
|---|---|
| `docs/topics/`, `docs/howto/`, `docs/tutorials/`, hand-written `docs/reference/` | `docs/adr/` — MADR template, own skill |
| `docs/developer/`, `docs/agents/` — same rules, maintainer audience | `docs/reference/code/` — mkdocstrings-generated |
| `_*.md` and `docs/includes/` **include fragments** — sentence- and block-scoped rules against the fragment; page-scoped rules (SG-07, SG-09, SG-10, SG-11, SG-12, SG-21, SG-32, SG-33, SG-39, SG-41, SG-44, SG-48, SG-50) against the page that includes it (DF-09-007, DF-09-008, ADR-0092) | `docs/reference/case_states/` — generated state pages |
| | `docs/reference/codebase/` — regenerated by `acquire-codebase-knowledge` |
| | `notes/`, `specs/` — own conventions (PD-01, MS) |

Generated pages are exempt. Fix the generator, not the output. Nav exclusion
(`not_in_nav` in `mkdocs.yml`) is not an exemption: it says which files get a
nav entry, not whether they are prose.

## 1. Terminology

**SG-01 — `glossary.md` is the arbiter.** `docs/reference/glossary.md` is the
canonical source for domain terms. Where a glossary term exists, use it.
Implements DF-09-002.

**SG-02 — Banned aliases.** The glossary's *Aliases to avoid* column is a
banned-synonym list. Do not write "responsible disclosure" for **CVD**,
"researcher" for **Reporter**, "supplier" for **Vendor**, or "stakeholder" for
**Participant**. Auto-fixable when the replacement is unambiguous.

**SG-03 — Concept names come from the taxonomy.**
`docs/reference/vultron-taxonomy.md` governs the concept names:
`vultron-core`, `vultron-wire`, `vultron-transport`, capability sets, capability
shapes, Vultron roles, Vultron-enabled applications. Write `vultron-core` for
the abstract protocol; write `vultron/core/` only when referring to the Python
package.

**SG-04 — Jargon that is not a domain term.** Field jargon absent from both the
glossary and the taxonomy must be expanded on first use, replaced with plain
language, or registered as a new glossary term. "Avoid jargon" and "use domain
language" are the same rule: the glossary decides which is which.

**SG-05 — Register new terms.** A page that introduces a durable domain term adds it to
`glossary.md` in the same change, and the page lists it under `introduces:` (SG-11). Do
not coin a term that nothing checks. For a term that needs discussion rather than a
definition, invoke `ubiquitous-language`.

**SG-06 — One name per concept.** Within a page, and across pages covering the
same concept, use one name throughout. Synonym variation for stylistic relief
is a defect, not a flourish.

## 2. Acronyms

**SG-07 — Expand on first use, per rendered page.** Write the expansion followed
by the acronym in parentheses at first use on each page: "Coordinated
Vulnerability Disclosure (CVD)". First use resets per page, because readers
arrive from search and from deep links, not by reading in nav order. "Page" means
the page as published, not the source file it was authored in — a page assembled
from `{% include-markdown %}` fragments has one first use, not one per fragment,
so this rule is evaluated against the assembling page and never against a
fragment on its own (DF-09-007, ADR-0092). Implements DF-09-003. An expansion
that the previous page in the nav also carries is this rule working, not
duplication (SG-44, DF-11-007).

**SG-08 — Register in the acronyms snippet.** Every acronym used in `docs/`
must appear in `docs/_acronyms/index.md`, which `pymdownx.snippets` appends to
every page to produce hover tooltips. If an acronym is missing, add it as part
of the change. Keep the file in strict alphabetical order, case-insensitive.
Ordering is a maintainability concern only — the `abbr` extension sorts its own
list by length descending before matching, so position in the file does not
affect which abbreviation wins. Auto-fixable.

**SG-08a — One definition per acronym.** `abbr` allows a single expansion per
token site-wide. Where a token is ambiguous, define it in the sense the docs
actually use, and check what a redefinition displaces before making it.

**SG-09 — Do not expand in headings.** Use the short form in headings and the
expansion in the first body paragraph that follows.

## 3. Concept order

Writing is a directed acyclic graph of topics: introduce an idea before the
ideas that depend on it. Within a page that graph is section order (SG-10);
across pages it is a hyperlink (SG-11) and the page's `level` (SG-40), and the
cross-page half is governed by `notes/site-information-architecture.md` § "Levels
100–500: a rule, not a label", whose rule is that no page may depend on a page
above its own level (DF-11-002).

**SG-10 — Within a page, no forward references.** No section may use a concept
the page has not yet introduced, defined, or linked out for. Ordering sections
so that each depends only on what precedes it is the page's primary structural
obligation. This is the within-page half of the dependency rule whose cross-page
half is the level rule in `notes/site-information-architecture.md` § "Levels
100–500: a rule, not a label" (DF-11-002): a concept the page cannot introduce in
order is linked out (SG-11), never assumed from a neighbor.

**SG-11 — Across pages, the edge is a hyperlink.** First use of a glossary or
taxonomy term on a page links to its canonical introduction — the glossary
entry, the taxonomy section, or the explanation page that develops it. The
glossary and the taxonomy are the concept registry; there is no separate
dependency file to maintain. The page that is a glossary term's canonical
introduction names the term in its `introduces:` frontmatter, and
`docs-level-order` fails an unlinked first use of it on a lower-level page
(DF-11-002), and `docs-thread-order` on a page earlier than the introducer on
a reading-path thread (DF-11-024). To find a term's introducer, run
`grep -rn "introduces:" docs/`.
If no page introduces the term, link to its glossary entry. Linking out is
what lets a lower-level page use a higher-level concept without violating the
level rule; the alternative is to re-level the page, never to leave the use
unlinked.

**SG-12 — Prerequisites are stated, not assumed.** A page that requires prior
reading says so in its opening paragraph and links to it. Tutorials and how-to
guides use an explicit `## Prerequisites` section (DF-04-008). State them even
when the previous page in the nav already did: a reader who arrived by deep link
never saw that page (SG-44, DF-11-007).

## 4. Sentence and paragraph shape

Simplified technical English in spirit, not ASD-STE100 compliance. The domain
vocabulary stays; the sentence complexity goes.

**SG-13 — One idea per sentence.** A sentence carrying two independent claims
becomes two sentences.

**SG-14 — Sentence length.** Target the corpus band: median 12–15 words, and
few sentences over 28. A sentence past 28 words is usually doing two jobs.

**SG-15 — Active voice with a named subject.** "The CaseActor commits the
entry", not "the entry is committed". Passive voice is acceptable when the
actor is genuinely unknown or irrelevant.

**SG-16 — Paragraphs run two to five sentences.** A paragraph that passes five
sentences is usually two paragraphs, or a list that failed SG-28.

---

## 5. Voice by agency

Voice follows the relationship between writer and reader, not a pronoun table.
Ask who has agency.

| Quadrant | Relationship | Pronouns | Spec |
|---|---|---|---|
| Tutorial | Tutor accompanying a learner | **we** for the shared journey; **you** for the learner's actions and state | DF-03-004, DF-03-011 |
| How-to | Practitioner owns the task | **you** and the imperative; author stays out of the way | DF-04-004 |
| Reference | Description of machinery | Neither. The system is the grammatical subject | DF-05-001, DF-05-007 |
| Explanation | Author discussing a subject | **we** for the author reasoning; **you** for inviting the reader to consider | DF-06-007 |

**SG-17 — Tutorial split.** "In this tutorial, we will run the demo" for the
journey; "You should now have three containers running" for what the learner
has and does. Do not write "We need Docker installed" — the learner needs
Docker, so it is "You need Docker installed".

**SG-18 — How-to imperative.** "Set `AUTH_MODE` to `oidc`. Run the service."
Not "We will configure authentication" and not "Let's set `AUTH_MODE`". The
latter changes the relationship from *here is the procedure you need* to *come
along while I teach you*.

**SG-19 — Reference describes, never instructs.** "A value of `0` disables the
timeout", not "Set `timeout` to `0` to disable it". Crossing from describing the
machinery into instructing the reader is the characteristic reference defect.

**SG-20 — Pronoun drift is a classification signal.** Out-of-quadrant pronouns
in isolation are a wording defect. Pervasive out-of-quadrant pronouns mean the
page is probably the wrong Diátaxis type: a how-to full of "we'll now explore"
is a tutorial or an explanation in the wrong tree, and a tutorial full of "you
should understand that" is drifting into explanation. Report these as
misclassification against DF-01-002; do not paper over them by swapping
pronouns.

## 6. Register

Practitioner to practitioner. Explains itself without teaching down; never
performs expertise. These rules are abstracted from the corpus, with
`docs/topics/actor-knowledge-model.md`, `docs/topics/background/what-is-vultron.md`,
and `docs/developer/how-to/run-tests.md` as the closest exemplars.

**SG-21 — Open declaratively.** The first line after the H1 states what the
thing is or does: "The protocol does not…", "Any Participant can…", "This page
explains…". No hooks, no rhetorical questions, no history first.

**SG-22 — Assertion, then consequence.** State the rule flat, then say what
follows from it. Short flat sentences in series carry the emphasis:

> There is no shared memory. There is no back channel. There is no way for one
> actor to look something up in another actor's store.

**SG-23 — Define by exclusion where it sharpens.** Saying what a thing is not
is a corpus habit worth keeping: "It is not a performance preference. It is not
an optimization. It is the architectural invariant on which the protocol is
built." Reference pages for concepts carry an explicit *What is out of scope*.

**SG-24 — No filler, hedging, or enthusiasm.** Banned: `simply`, `just`,
`obviously`, `of course`, `note that`, `it should be noted`, `basically`,
`clearly`, exclamation points, and rhetorical questions outside a
`!!! question` admonition. Confidence comes from flat declaratives, not
adverbs. Auto-fixable by deletion where the sentence survives it.

**SG-25 — Cite instead of asserting.** A normative claim carries its identifier
inline: `(AKM-02-001, AKM-02-002)`, `(ADR-0048, CM-18-003)`. Unattributed
"must" in explanation prose is a finding — either it is normative and has an ID,
or it is advice and should not say "must". A link to a Protocol Specification
section carries the section's number and name, as in "§6 Report Management (RM)
State Machine", never a bare "§6" or "section 6", and
`test/metadata/docs/test_spec_citations.py` fails on a bare one.

**SG-26 — Emphasis discipline.** Bold marks the term being defined, sparingly.
A blockquote carries the one load-bearing invariant of the page, not general
quotation. Italics for the first mention of a work or for genuine contrast.

**SG-27 — Admonitions in proportion.** The corpus runs `note` ≫ `tip` > `info` >
`example` > `question` > `warning`. Reserve `warning` for real hazards — data
loss, embargo breach, protocol violation. Do not inflate it for emphasis.

## 7. Lists and tables

**SG-28 — A bulleted list requires parallel membership.** Items must be
parallel members of one set: roles, fields, options, states. Reasoning,
cause and effect, and comparison go in prose. Bullets that each carry a
sentence of argument are a paragraph that lost its connectives.

**SG-29 — Ordered lists mean ordered.** Numbered lists are for steps executed
in sequence, or for enumerated items referenced by number elsewhere on the
page. Do not number an unordered set.

**SG-30 — Tables beat bullets for pairs.** Term and definition, property and
value, state and meaning: use a table. The corpus does this consistently and
the result is scannable.

**SG-31 — Quadrant exemption.** How-to and tutorial bodies are exempt from the
sparing rule. Their steps are inherently sequences and their prerequisites are
inherently sets.

## 8. Diagrams

**SG-32 — A diagram earns its place.** Add one when it shows a relationship
that prose would need three or more cross-references to convey: a state
machine, an inter-actor sequence, containment or composition, a lifecycle. No
page is owed a diagram, and no cap applies — a process-model page legitimately
carries eight.

**SG-33 — Prose must stand alone.** Every diagram has an adjacent sentence
stating what it shows, before or immediately after it. The page must remain
comprehensible when the render fails, in print output, and to a screen reader.

**SG-34 — Mermaid, with a title.** Diagrams use fenced `mermaid` blocks with a
`---` / `title:` header, which supplies the rendered caption.

**SG-35 — Sanctioned diagram types.** `stateDiagram-v2`, `sequenceDiagram`,
`flowchart`, `classDiagram`, `erDiagram`. Legacy `graph` is `flowchart` and is
auto-fixable. Anything outside this list needs a reason.

**SG-36 — Prefer Mermaid to ASCII art.** New structural diagrams use Mermaid.
Existing ASCII diagrams in `text` fences are grandfathered and reported as
low-priority findings; do not auto-convert them.

## 9. Mechanics

**SG-37 — American spelling.** `organize`, `behavior`, `normalize`,
`serialize`. Auto-fixable in prose. Existing filenames and ADR titles are
grandfathered — do not rename `adr/0062-normalise-wire-to-core-*` or
`reference/messages/faults_and_acknowledgements.md`. Mechanical enforcement:
`codespell` over `docs/`, configured in `[tool.codespell]` in `pyproject.toml`
(`builtin = "en-GB_to_en-US"`) and run by the `codespell` pre-commit hook with
`--write-changes`. The dictionary has no notion of a code fence, an inline code
span, a cited external title, or an include or link target, so a token that
must stay as written (a third-party API name such as
`py_trees.behaviour.Behaviour`, a paper or standard's title, a proper noun such
as the National Cyber Security Centre) is protected by `ignore-regex`, never by
hand-editing around the hook (ADR-0092).

**SG-38 — One sentence per line.** On pages that `write-docs` creates or
rewrites, each sentence starts on its own line with no mid-sentence hard wrap.
Prose diffs then show which sentence changed. Pages not touched by a change are
left as they are; the corpus is mixed by design, and no line-length rule
applies.

**SG-39 — Headings.** One H1 matching the nav label in substance. H2 and below
in sentence case. Sections separated by `---` where the page has more than
three of them, following the corpus.

**SG-40 — Frontmatter declares audience, level, page type, subject, and
introductions.** Every reader-facing page declares `stakeholder_type`, a `level`
from 100–500 (DF-11-001), a `page_type` (DF-11-018): its Diátaxis quadrant, or
`routing` for a page that mainly gives directions, and a `subject` (DF-11-025):
`protocol`, `implementation` or `neutral`. A working-record page declares
`stakeholder_type: [project-contributor]` and no `level` (DF-11-012),
`page_type` or `subject`. An include fragment declares none of them, because it
takes its hosts' declarations (DF-11-010). A page that is
the canonical introduction of a glossary term lists it under `introduces:`
(SG-11). `docs-frontmatter`, `docs-nav-subjects`, `docs-level-order` and
`docs-thread-order` enforce these.

`subject` says what the page is **about**: the protocol (its specification,
requirements, messages, models and design, including a tutorial that teaches
protocol behavior on the reference implementation), CERT/CC's reference
implementation (its code, demos, architecture and project record, however
protocol-shaped), or neither. `neutral` pages may sit in any nav section, but
`docs-nav-subjects` fails a nav section that holds both a `protocol` and an
`implementation` page (DF-11-020), so a page belongs in a section of its own
subject. Fix a failure by moving the page, or by correcting a wrong `subject`,
never by declaring `neutral` to get past it. Where `title`
and `description` are present, keep them accurate, but do not add other keys
that nothing reads.

`stakeholder_type` names **who the page is addressed to**, drawn from the
members in `docs/includes/stakeholder_types.md`. It is not a **CVDRole**. A role
(Reporter, Vendor, Coordinator, Deployer, …) is a position an actor holds in one
case — assumable, inhabitable, temporal — while a stakeholder type is why a
reader is here, and no value appears in both vocabularies. A page tagged
`vendor` or `coordinator` has reached for the wrong list; `docs-frontmatter`
rejects it, and the fix is to pick the type, never to add the role
(`notes/site-information-architecture.md` § "Stakeholder type is not CVD role").

The audience and level are declared, never rendered. The page's own `level` and
`stakeholder_type` do not appear in its prose, headings, admonitions, or nav
label (DF-11-004, DF-11-009). The orientation paragraph (SG-41) says who the
page is for in the reader's situation — "if you are wiring a tracker into a
case" — not by the type's name. The `page_type` is the opposite: the site
renders it as a badge above the title (DF-11-019), so a page never states its
own type in prose or writes a type badge by hand.

**SG-41 — Page furniture.** H1, then a two-to-four sentence orientation
paragraph saying what the page covers and who it is for, then the body. Where a
page closes with a recap, use a `## Summary` table of principle and statement,
a `## Further reading` link list with em-dash annotations, or both.

**SG-42 — No page length rule.** Pages are split by quadrant and topic, never
by length. A long reference page is correct; a three-paragraph explanation page
is correct.

**SG-43 — Shared content is included, not copied.** A paragraph, table, or
diagram that belongs on more than one page becomes an `{% include-markdown %}`
fragment — a `_<slug>.md` file beside its hosts, referenced by a path relative to
each including file. Never copy the block. A copy passes lint on both pages
because neither is wrong by itself, then drifts when one is updated. Reported,
never auto-fixed: whether the duplication is intentional is the author's call.
A drifted near-copy is the same finding: merge it into one fragment, keeping the
wording that is correct against its authority, unless a documented reason keeps
the two apart (DF-10-002). Normative anchors: DF-10-001, DF-10-002. SG-44 names
the repeats that are never a finding under this rule: a page introducing itself
in its own words, and its acronym expansions (SG-07).

**SG-44 — Self-sufficient on arrival.** A page must make sense to a reader who
lands on it from a search result or a deep link and has read none of its nav
neighbors. Concretely: the orientation paragraph says what the page covers
(SG-41), the prerequisites are stated and linked (SG-12), and every acronym is
expanded at first use on this page (SG-07). The nav neighbors are irrelevant to
the check, and so is the fact that the previous page carries the same opening,
the same prerequisite sentence, or the same expansion. **An opening, a restated
prerequisite, or a re-expanded acronym that also appears on an adjacent page is
compliant on the rendered page; never remove it.** Deleting one to make two
pages read as a continuous sequence degrades every deep-link arrival and is a
regression, whatever it does for the one reader who starts at the top. The rule
governs the rendered page, not the source: a block sourced from one fragment
that each page includes satisfies it, and where the source lives is a separate
SG-43 question. A page introducing itself in its own words — prose
describing this page, not content another authority owns — stays inline and is
never an SG-43 copy. A block one authority owns (a banner, a pointer, a shared
prerequisite list) is an SG-43 copy even when it serves arrival, and becomes a
fragment that every page still renders. Page-scoped:
evaluated against the assembly unit, never a fragment (DF-09-007). Implements
DF-11-007; rationale in `notes/site-information-architecture.md` § "Pages stay
self-sufficient; nav order carries dependency".

## 10. Visual components

A page may break up its text with the components below, and with no others
(ADR-0136). Each rule says when to use the component and when not to. A
component used where its rule does not fit is a finding, reported with the
plain-prose alternative.

**SG-45 — A closed set.** The approved components are content tabs, code
annotations, card grids, grids (the plain grid and the two-column grid), buttons,
and the page-type badge. The theme provides all of them but two: the
two-column grid's class lives in `docs/stylesheets/components.css`, and the
badge is rendered by a template (SG-51). Do not add inline `style=` attributes,
hand-built HTML layouts, or a component class outside those stylesheets. A new
component needs a rule in this section before any page uses it. Two components
are rejected and are not to be added: a "who this page is for" strip, because
naming the page's audience exposes its stakeholder type (DF-11-009), and an "in
brief" summary box, because the orientation paragraph already does that job
(SG-41). The home page's hero is part of the home-page template, not a
component a page places, so it is outside this set and SG-50 does not govern it.

**SG-46 — Content tabs: parallel views of one subject.** Use `===` tabs
(`pymdownx.tabbed`) when one subject has views a reader wants one at a time,
such as a message's reference facts and its example JSON. Each tab must make
sense alone. Do not use tabs for steps that run in sequence (SG-29), for
content a reader must compare side by side, or for a single tab. Keep headings
outside a tab set, so an anchor never depends on which tab is open. The site
links tabs by label (`content.tabs.link`), so give the same view the same label
everywhere on a page. The message reference sections render their facts and
example as tabs from `msm-occasions`; change the generator, not the fragments.

````markdown
=== "Details"

    - **Send:** `Offer(VulnerabilityReport)`

=== "Example activity"

    ```json
    { "type": "Offer" }
    ```
````

**SG-47 — Code annotations: notes on one example.** Use numbered annotations
(`content.code.annotate`) when a wire example needs a note tied to a particular
field. Write the marker as a trailing comment in the block's language, such as
`// (1)!` in JSON or `# (1)!` in Python or YAML, and the notes as a numbered
list immediately after the block. An annotation states a fact about
this example; field semantics shared across examples go in a table instead
(SG-30). The notes are hidden until opened, so nothing the reader needs to
understand the example may live only in one. Do not annotate a generated
example: change its generator.

**SG-48 — Card grids: a set of destinations.** Use
`<div class="grid cards" markdown>` around a list on a routing or landing page,
one card per destination or step, each a link with one line saying what is
there. A content page may close with one card grid of where to go next. Do not
use cards for a page's argument, or for an ordered sequence, which is a
numbered list (SG-29). A generated section listing (DF-11-005) may sit inside a
card grid; keep the `<div>` outside the generated markers.

**SG-49 — Grids: things a reader compares side by side.** Use
`<div class="grid two-col" markdown>` with exactly two `<div markdown>`
children, the diagram first, when a diagram and the table or list that decodes
it belong side by side. The first column is wider, and the grid collapses to
one column on narrow screens. For figures of equal weight shown side by side,
such as two charts of one data set, use the theme's plain
`<div class="grid" markdown>`, which fits as many columns as the screen allows.
Do not use either for columns of prose. Each diagram or figure still needs its
adjacent sentence (SG-33), outside the grid.

**SG-50 — Buttons: at most two, at the top of a landing page.** Use
`{ .md-button }` on a link for the primary destinations of a landing or start
page, directly after the orientation paragraph: at most two, the first marked
`.md-button--primary`. Label a button with what the reader does there, such as
"Send your first message". Do not use buttons in body prose, on a content page,
or to make an ordinary link stand out.

**SG-51 — The page-type badge is rendered, never written.** The site draws the
badge above the title from the page's `page_type` (DF-11-019), and a `routing`
page shows none. Its styles are in `docs/stylesheets/page_type.css`. Never write
a badge by hand, and never state the page's type in prose (SG-40).

## Escalation

Both skills fix mechanical findings silently and escalate judgment calls with a
recommendation, never as an open question. State the finding, state what you
would do about it and why, and ask for confirmation. This applies to quadrant
misclassification (SG-20), cross-quadrant page splits (DF-01-003), and nav
placement alike. A nav-placement recommendation is argued from the page's
`level` and `stakeholder_type` against `notes/site-information-architecture.md`
(see `write-docs` Phase 6), so the reviewer can check it rather than weigh it.
