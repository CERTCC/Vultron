# Vocabulary Registry — Design Rules

Operating rules: `vultron/wire/as2/vocab/AGENTS.md`. Specs:
`specs/vocabulary-model.yaml`. Implementation:
`vultron/wire/as2/vocab/base/registry.py`.

## Registration

### 1. Auto-registration via `__init_subclass__`

`as_Base.__init_subclass__` registers every subclass that narrows `type_` to a
`Literal[...]`, at class-definition time; no decorator. Abstract bases
(`as_Object`, `as_Activity`, `as_Actor`, …) leave `type_` as `str | None` and are
skipped.

### 2. A concrete class MUST narrow `type_` to a `Literal`

`set_type_from_class_name` (VM-03-001) derives `type_` at construction for a
class with no annotation, but registration skips it, so the two mechanisms
disagree about which classes are concrete and registration is the silent one
(VM-03-002). `test_registry.py::TestWireTypeValues` walks the `as_Base`
subclasses and requires each class presenting its own type value to be what
`WIRE_TYPE_MAP` answers, with a per-class exemption set whose members each name
a reason.

### 3. Flat registry dict

The registry is one flat `dict[str, type[as_Base]]`; objects, activities and
links share one namespace with no collisions.

### 4. `VocabNamespace` is not a key, but it is load-bearing

Each `as_Base` subclass carries `_vocab_ns: ClassVar[VocabNamespace]`
(default `AS`; `as_VultronObject` sets `VULTRON`). The type name alone is the
key, because callers usually hold only the wire `type` string. But `_vocab_ns`
is the sole input to the generated JSON-LD `@context`, so a Vultron-specific type
left annotated `AS` ships without a `vultron:` term and receivers cannot resolve
it (VM-10-001, VM-10-002).

### 4a. Declaring a Vultron extension term

A wire type or property becomes a Vultron extension term only when no context
Vultron cites defines a term with its meaning. Otherwise it reuses that term, and
it never takes a cited term's name for another meaning (VM-10-009;
[activitystreams-semantics](activitystreams-semantics.md) § "Choosing AS2 Terms").
Every extension term is declared, never inferred: ADR-0194 decides this for
properties, and a type is declared by its class. Each part of the declaration has
one home:

| Case | On the class | Generated by `wire-context` | By hand in `docs/ns/index.md` |
|---|---|---|---|
| New type `X` | `type_: Literal["X"]` on a core class registered in `WIRE_TYPE_MAP`, or on a wire class annotated `_vocab_ns = VULTRON` | `"X": "vultron:X"` in `context.jsonld`; `schema/types/X.json` (VM-10-006, #6064) | a row under "Declared types" |
| Subtype `X` of AS2 type `T` | as a new type, plus `_as2_core_supertype = as_T` on a wire class (§ 5a) | as a new type, plus `vultron:X` `rdfs:subClassOf` `as:T` in the document's `@graph` (`vultron_subtype_statements`) | the row, naming `as:T` in a "Subtype of" column |
| New property `p` | `vultron_property(definition, kind)` on each field sent as `p` | `"p"` → `vultron:p`, typed by its value kind (VM-10-010); its row in `index.md`'s "Declared properties" table | nothing |
| Retired term | the class, or the marked field, deleted | the term, any schema and a property's row removed | a type's row deleted |

`test_namespace_index_page_lists_exactly_the_generated_terms` holds the
hand-written type rows to the generated terms, and
`test_namespace_index_page_names_each_types_supertype` holds the "Subtype of"
column to the `@graph`.

**New type.** A domain type is a core class with a `Literal` `type_`, registered
by one line in its wire module (`WIRE_TYPE_MAP["VulnerabilityReport"] =
VulnerabilityReport`); it carries no `_vocab_ns` (ARCH-25-003). A wire-only class
is annotated `_vocab_ns = VocabNamespace.VULTRON` (§ 4). It is sent with one
`type` value. Its fields reuse AS2 properties where AS2 has the meaning, so they
need no term (the planned `Redacted` marker's `summary`, #6372). A class that
shares another class's `type` value declares `_wire_type_alias = True` and gets no
term (VM-01-014). Add its canonical example under
`vultron/wire/as2/vocab/examples/`.

**Subtype of an AS2 type.** A new type is a subtype when each of its instances is
also an instance of one specific AS2 type, so a plain AS2 reader that sees only
that type still reads the message correctly: `Refuse` is a `Reject` (ADR-0196),
and `EmbargoEvent` is an `Event`. A type whose nearest AS2 type is `Object` is a
new type, because `Object` tells a reader nothing it can act on. The class
declares its AS2 supertype explicitly; its Python base does not decide it, because
a core class never extends a wire class. One declaration feeds three readers,
all built for a wire class (§ 5a; `as_Refuse` is the first user). A core class
such as `EmbargoEvent` cannot declare one yet: `_as2_core_supertype` must be an
ancestor, because the resolver's "most specific" test is `issubclass` (#5155):

- the serializer writes `"type": ["X", "T"]`, because AS2 Core § Extensibility
  asks an extension type that overlaps a core type to carry the core type too;
- the received-type resolver narrows that list, in any order, to `X` (ADR-0196);
- the generator writes the subclass statement into the context document's
  `@graph`, beside its `@context`:

```json
"@graph": [
  {
    "@id": "vultron:Refuse",
    "http://www.w3.org/2000/01/rdf-schema#subClassOf": {"@id": "as:Reject"}
  }
]
```

A processor that loads the document as a remote context reads only its
`@context`, so the `@graph` changes no term a message resolves. The predicate is a
full IRI because neither the AS2 context nor Vultron's defines an `rdfs` prefix,
and adding one would add a term to every message.

**New property.** Mark each field the property travels on, after checking that no
cited context has a term with its meaning (VM-10-007, VM-10-009). Every Vultron
wire field carries the marker; a field without it must be a term a cited context
defines. The marker is `json_schema_extra=vultron_property(definition, kind)`
(from `vultron.core.models.base`, re-exported by the wire base). The definition
is the property's meaning in one line, and the kind is its value's shape, which
the term is typed from (VM-10-008, VM-10-010):

| `PropertyValueKind` | Value | Term |
|---|---|---|
| `PLAIN` | a literal or an embedded object | `"vultron:p"` |
| `IRI` | an IRI, or an object that has one | `"@type": "@id"` |
| `JSON` | a received document kept verbatim | `"@type": "@json"` |
| `LIST` | an array whose order matters | `"@container": "@list"` |
| `SET` | an array whose order does not | `"@container": "@set"` |
| `INDEX` | a map keyed by IRIs | `"@container": "@index"` |

A container kind takes `items=PropertyValueKind.IRI` when its values are links,
which adds `"@type": "@id"`. Two declarations of one wire name agree on both
(VM-10-012), so a name declared on several classes is one shared constant
(`LEDGER_POSITION_PROPERTY`, `CASE_STATUS_PROPERTY`), and the generator refuses
two that disagree. The generator keys the term by the field's wire name
(`vultron_property_terms`). It walks core classes too, because a paired type's
wire class is its core class (ARCH-25-003): a case's `ledgerPosition` is marked
on `VulnerabilityCase` (SYNC-16-005). An unmarked Vultron property has no term,
so a receiver cannot resolve it.

**Retired term.** Delete the class, or the field that carries the marker, and
regenerate: the term leaves `context.jsonld`, a type's schema leaves
`schema/types/`, and its row leaves `index.md`. Keep no deprecated entry, alias or
`owl:deprecated` mark. Before 1.0 there is one wire version, so a peer that still
sends the term gets the ordinary handling: a retired type is an unknown type, and a
retired property is an unknown key (ADR-0175). Once the context document has its
versioned URL, a retirement is an incompatible change and bumps the wire version
(ADR-0106). The ontology's record of retired classes is not part of this rule
(#6423).

**The document is generated, never hand-edited.** `uv run wire-context --write`
(`vultron/metadata/wire_context/sync.py`) writes its type terms from every wire
class whose `_vocab_ns` is `VULTRON` and every core class `WIRE_TYPE_MAP`
registers whose `type` is not an AS2 term, keyed by the emitted `type` value, so a
class sharing another's `type` needs no term of its own. It writes its property
terms from the marked fields of the same classes and of every model nested in them
(`wire_field_classes`), skipping `exclude=True` fields and a model that serializes
as one value (a status dimension). It also writes the "Declared properties" table
of `docs/ns/index.md` from the definitions. When adding, renaming or retiring a
term:

- Regenerate and commit both artifacts. `uv run wire-context --check`
  (pre-commit) and `test_committed_context_is_not_stale` (CI) enforce it.
- Annotate a Vultron-specific type `VULTRON`.
  `test_non_as2_wire_types_are_annotated_vultron` checks against the AS2 term set
  from the *defining module*, never from `_vocab_ns` itself, which would blind
  the guard to the mistake it looks for.
- Keep the enumeration filter to classes defined under `vultron.wire.as2.vocab`,
  plus the core classes `WIRE_TYPE_MAP` registers from `vultron.core.models`
  (`CORE_MODELS_PACKAGE`): a class declared inside a test joins the subclass
  graph, and without the filter a test probe could inject a term into the
  normative document.

The document is normative but not reachable: `ns/` stays withheld from the
published site until #3653 moves it to the versioned URL ADR-0106 decided, and
`uv run docs-withheld` fails CI if a build publishes it (DOCBW-03-005).

### 5. Lookup fails fast on unknown types

`find_in_vocabulary()` raises `KeyError` for an unregistered name (VM-06-005):
a silent `None` lets corrupt deserialization proceed. A caller that should skip
unknown types catches `KeyError`.

### 5a. A received `type` goes through `resolve_wire_type()`

A received `type` may be an AS2 list. Read it only through `resolve_wire_type()`
(or `resolved_wire_type_name()` to compare or report a name), never with
`isinstance(type_, str)` and a bare `find_in_vocabulary()`: the resolver narrows
a list to its most specific known class, ignores unknown terms, and raises
`AmbiguousWireTypeError` (a `KeyError`) on two unrelated known types
(VM-03-006, VM-03-007). Validate a dict whose `type` may be a list through
`narrow_type_list()` first, because a core class's `type_` holds one string. An
extension class that refines an AS2 core class declares
`_as2_core_supertype = <AS2 class>` with `_vocab_ns = VocabNamespace.VULTRON`;
its wire dump writes `[own type, core type]` and its persistence dump keeps one
string (VM-03-005, ADR-0196).

A class that validates a list naming its own declared type reads the list as that
type, so `as_Reject` can re-read a `Refuse` dump; the semantic coercion of a
stored row does exactly that (`coercion.py`). A core reader asks whether a body
*names* a type through `vultron/core/models/type_terms.py`, which the wire edge
shares for its term rule, because core cannot ask which term is most specific
(ARCH-01-001).

### 6. Dynamic discovery is the startup guarantee

`vocab/objects/__init__.py` and `vocab/activities/__init__.py` import every
sibling module with `pkgutil.iter_modules`, because `__init_subclass__` fires
only for classes that are defined, and a never-imported module defines none.

## `CORE_TYPE_MAP` Is Core-Only

Core types never enter the wire `VOCABULARY` (ARCH-12-014). `CoreRecord` and
`CoreObject` subclasses auto-register in `CORE_TYPE_MAP`
(`vultron/core/models/registry.py`). The hook lives on `CoreRecord` because the
bookkeeping records extend it but not `CoreObject` (ARCH-12-010); ratchets
`test_core_record_types_in_core_type_map` and
`test_no_wire_types_in_core_type_map` hold both directions.

`find_in_vocabulary()` is wire-only unless the caller passes
`include_core=True` (VM-06-013). Only persistence read paths ask for the core
fallback. A wire-side caller must not (MV-04-004): a core class placed in a wire
tree is rejected by the parent's field type, so the fallback degrades the parent
instead of resolving the child. A hit there is a coincidence of naming, not a
wire counterpart. See [wire-core-boundary](wire-core-boundary.md).

A core collection model MUST NOT be reintroduced: `CoreActor.inbox` and
`.outbox` are URL strings (ARCH-12-006), and a core class declaring
`type_: Literal["OrderedCollection"]` squats the wire name in `CORE_TYPE_MAP`.

## Actor Overrides Keep `"Actor"`

A Vultron actor module overrides only the concrete actor keys it needs
(`Person`, `Organization`, `Service`, …); `"Actor"` stays mapped to `as_Actor`,
its only registration. The VM-01-007 ratchet refuses an `as_Actor` left
unreachable.

## Registry Keys Are Disjoint: `VOCABULARY` vs. `WIRE_TYPE_MAP`

Wire classes use the `as_` prefix (ARCH-14-001), but for a *domain* type the
prefixed name is an alias of the core class (ARCH-25-003) and holds no
`VOCABULARY` key. The prefix still marks a real wire class for unpaired AS2
vocabulary (`as_Link`, `as_Collection`, …).

| Registry | Key | Example | Spec |
|---|---|---|---|
| `VOCABULARY` | full `as_*` class name | `"as_Collection"` | VM-01-004 |
| `WIRE_TYPE_MAP` | emitted wire `type` value | `"Collection"` | VM-01-008 |

Only `WIRE_TYPE_MAP` answers a `type` lookup: `find_in_vocabulary()` never
consults `VOCABULARY`, so an inbound `"type": "as_Activity"` is an unknown type
(VM-01-016). Do not rely on a class's `type_` annotation to refuse its own class
name: `as_Activity.type_` is a bare `str` and refuses nothing (#5738).

Both keys are derived by `as_Base.__init_subclass__`, `WIRE_TYPE_MAP` via
`wire_type_value()`. Two classes cannot own one `type` value, so a class that
shares another's declares `_wire_type_alias: ClassVar[bool] = True` and takes no
`WIRE_TYPE_MAP` key. The Vultron actor classes (`as_VultronPerson`, …) are
the only sanctioned unflagged sharers: they register after the base actors and
shadow them, so `{"type": "Person"}` gets the subclass carrying
`embargo_policy`. A core class may own an AS2 `type` whose wire class stays a base
for others: the attached-file classes own `Document`, `Image`, `Audio` and `Video`,
and `as_Document` and its file subtypes declare `_wire_type_alias`, so the owner
does not depend on import order (CSAF-01-001). The ratchet fails on any other
collision, which would silently move the key to whichever class imports last
(`test/architecture/test_vocab_registry_keys.py`; disjointness from
`CORE_VOCABULARY` in `test/wire/as2/vocab/base/test_registry.py`). Do not
restate a key count in prose (MS-16-001).

**Never resolve a core type's wire counterpart by name.** Under ADR-0099 there
is none: `render()` is the object's own `model_dump` (ARCH-20-002), and the
declarative pairing registry (ARCH-23-001) was cancelled, not deferred; do not
revive #2937. `test_render_adapter_does_not_resolve_a_wire_counterpart` and
`test_package_does_not_resolve_a_wire_counterpart` refuse every name in
`REGISTRY_LOOKUP_NAMES` (`test/support/source_names.py`) in the render and
trigger adapters. They match direct name references only.
