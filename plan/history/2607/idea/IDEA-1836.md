## Summary

The current received-side status pipeline handles inbound `Add(ParticipantStatus)`
activities and triggers embargo teardown for CS.P via `PublicDisclosureBranchNode`.
However, the authorization model is wrong (CASE_OWNER gate is in the wrong tree),
CS.X and CS.A do not trigger teardown, and there is no hook for the CaseActor to
exercise judgment before adopting a participant's reported CaseStatus as canonical.

This Idea supersedes #1250 (`create_monitor_threats_tree` polling factory), which
correctly modelled the simulation architecture but maps to the wrong pattern in
production. In production, threat monitoring is event-driven: an external sentinel
actor posts `Add(ParticipantStatus)` with PXA state changes; the CaseActor
received-side pipeline decides whether to adopt those changes and whether to
execute side-effects (embargo teardown).

## Two-Seam Design

### Seam 1 — StatusUpdateGuard (in `add_participant_status_tree`)

After `AppendParticipantStatusNode` records "participant X said FOO", a new
`StatusUpdateGuard` Fallback decides whether to canonicalize that reported
CaseStatus:

```text
StatusUpdateGuard (Fallback)
├─ CheckIsCaseOwnerNode       ← hard bypass: CASE_OWNER is gospel
└─ CaseOwnerApprovesStatusUpdate  ← Evaluator call-out (AlwaysSucceed default)
```

If the guard passes, the CaseActor emits a self-addressed
`Add(CaseStatus, VulnerabilityCase)` to itself (as CASE_MANAGER), which
canonicalizes the approved status update through the existing
`add_case_status_tree` pipeline.

### Seam 2 — SideEffectsGuard + ThreatTerminationBranchNode (in `add_case_status_tree`)

After `AppendCaseStatusToCaseNode` writes the canonical state, a new
`SideEffectsGuard` Evaluator call-out (AlwaysSucceed default) gates execution
of `ThreatTerminationBranchNode`, which extends the current
`PublicDisclosureBranchNode` to cover CS.P, CS.X, and CS.A.

The `PublicDisclosureBranchNode` in `add_participant_status_tree` is moved
here and extended.
