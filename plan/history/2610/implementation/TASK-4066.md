The owner-Leave arm of `create_close_case_received_tree` now runs
`ExpirePendingInvitesOnCloseNode` between the CASE_MANAGER's `RM.CLOSED` entry
and `case_fully_closed` (CM-23-014). For each `INVITED` row on an open
register entry (`EmbargoLifecycle.pending_invitations`), it runs the late-Accept
path's own commit -> effect subtree, now extracted as
`create_commit_and_record_expiry_tree`. That gives one
`invite_to_embargo_on_case_expired` entry, then `INVITED -> TIMED_OUT` via
`record_invite_expiry`. Replicas replay it through the existing
`ApplyInviteExpiryFromLedgerNode`, so no new event type or apply node was
needed (RSH-08-004).

Rows on final register entries are frozen (ADR-0122) and are not settled. That
covers a stub invitee's row on the embargo the close already required to end.
Recording is best-effort, like the `RM.CLOSED` entry: a refused commit never
costs the case its `case_fully_closed`.

The issue text named an `invite_to_embargo_on_case_lapsed` entry; the strict
xfail it pointed at checks the real CM-28-009 type, `INVITE_EXPIRED_EVENT_TYPE`.
