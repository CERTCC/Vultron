# Vultron Project — October 2026 Work Sponsor Report

## Executive Summary

October 2026 settled more of the Vultron protocol's design than any month so far. About 40 new architectural decision records (ADRs, the project's written record of each design choice) were added. Together they answer questions the September specification left open:

- What a participant's copy of a case actually is.
- What happens when messages arrive out of order.
- Who has authority to change which parts of a case.
- How an embargo is tracked once several versions have been proposed.

The protocol specification was audited requirement by requirement and is now published as a multi-page document with its own requirements catalog. The documentation site was reorganized around who is reading and why, instead of by document type. On October 23 the project published [v2026.10.0](https://github.com/CERTCC/Vultron/releases/tag/v2026.10.0), its first tagged release since 2024, which packages the reference implementation for research and evaluation.

The month merged 642 pull requests and closed 843 issues. Several decisions are still marked provisional or proposed, and message signing is designed but not built. Both are flagged below.

## What We Now Know About the Vultron Protocol

In September the specification described the messages and state machines, but left several questions about shared case state either unanswered or answered only by how the code happened to behave. Each answer below is now a written decision. Most are *accepted provisionally*, meaning they are backed by passing tests and open to revision before final human sign-off.

### A participant's copy of a case is defined by the case ledger

**Before:** each participant kept its own copy of a case and ran the protocol's decision logic itself to keep it up to date. Nothing in writing said what should happen if two copies disagreed.

**Now settled:**

- **The ledger defines the case.** A case is defined by its case ledger, the append-only, hash-chained log of every change to the case. Each copy is just the result of applying that log in order. Any two participants that have applied the same entries hold the same case, and a copy never makes its own decisions ([ADR-0124](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0124-case-is-a-projection-of-its-ledger.md)).
- **What belongs in the shared record.** The *case file* (reports, participants, status, embargoes, consent, notes) is shared through the ledger. The case manager's private working records are not.
- **Ordering.** The protocol's ordering guarantee is *eventual consistency*. Messages may arrive in any order, and every copy still reaches the same state. No implementation may rely on in-order delivery for correctness ([ADR-0161](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0161-eventual-consistency-is-the-protocols-ordering-guarantee.md)).
- **Detecting and repairing drift.** Every case message states how far along its sender's ledger is. That lets the case manager spot a participant that has fallen behind and bring it up to date ([ADR-0155](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0155-a-participant-states-its-ledger-position-and-the-case-manager-answers-a-lag.md), [ADR-0156](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0156-every-case-activity-states-its-senders-ledger-position.md); decisions still marked proposed). A participant whose copy has diverged is repaired with a fresh copy of the case that names its exact ledger position ([ADR-0142](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0142-a-diverged-replica-is-repaired-by-a-fresh-case-copy-that-names-its-ledger-position.md)).
- **Creating a case.** A case's creation is a single message, delivered to participants and recorded as the first ledger entry ([ADR-0157](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0157-a-cases-creation-is-one-create-delivered-and-ledgered.md)).

**What we learned:** the project reviewed the code for places where behavior depended on message order. Its rule is that each one found is a bug to fix, not a reason to weaken the guarantee. Separately, an automated architecture check found one replica path that still ran embargo decision logic instead of copying, and it was fixed ([PR #4838](https://github.com/CERTCC/Vultron/pull/4838)). Every tracked multi-party scenario is now rebuilt from the case manager's ledger alone and checked against the original.

### Who may do what is spelled out per message

- **Two roles.** *Case Owner* (the party accountable for the case) and *Case Manager* (the service that keeps the authoritative record and relays messages) are now defined as separate roles in the [glossary](https://github.com/CERTCC/Vultron/blob/main/docs/reference/glossary.md) ([PR #5016](https://github.com/CERTCC/Vultron/pull/5016)).
- **Sender rules.** Every message type declares which senders may send it, and the receiver checks that declaration ([ADR-0115](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0115-received-handlers-check-sender-entitlement.md), [ADR-0129](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0129-a-sender-rule-states-every-position-on-both-sides-and-is-the-source-of-sent-by.md)).
- **Message type vs. permission.** When the case manager performs the same action as a participant, its message has the same type. Whether a sender is *allowed* to send a message is checked separately from what kind of message it is. Records of things merely observed, such as an expired offer, are not added to the ledger ([ADR-0152](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0152-a-case-managers-act-shares-the-participants-semantic-type-and-an-observation-is-not-ledgered.md)).
- **Reporters.** The organization that received a report now introduces the case manager to the reporter, so the reporter can trust messages from a service it has never dealt with ([ADR-0132](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0132-the-report-receiver-introduces-the-case-manager-to-the-reporter.md)).
- **Refusals.** A refused message is answered with a Reject of that exact message, so the sender always learns the outcome ([ADR-0141](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0141-a-refused-assertion-is-answered-with-a-reject-of-the-refused-activity.md)).
- **Ownership transfer.** The owner proposes the transfer, and the case manager makes the formal offer ([ADR-0148](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0148-an-owner-proposes-an-ownership-transfer-offer-and-the-case-manager-makes-it.md); implemented, decision still marked proposed).

### Embargoes have a full history and consent per version

- **The embargo register.** A case keeps a register of every embargo version proposed, activated, revised, or ended, and its current embargo state is computed from that register ([ADR-0130](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0130-em-is-computed-from-the-embargo-register-under-the-em-transition-table.md); implemented, decision still marked proposed).
- **Consent per version.** Each participant's consent is recorded separately for each version. A Case Owner can therefore see exactly who agreed to which terms.
- **New steps.** A participant can now withdraw from the embargo in force. An embargo ends on its own when its end time passes, and the reason it ended is recorded.
- **Public information ends the embargo.** When a case records that a vulnerability is public, that an exploit is public, or that attacks have been seen, the embargo ends in that same step ([ADR-0166](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0166-adopting-p-x-or-a-and-ending-the-embargo-are-one-authorized-step.md)). **What we learned:** a separate permission check for ending the embargo protected nothing that the earlier check didn't already cover, and keeping it allowed a contradictory state: a case that records a secret as public while telling participants to keep it.
- **Case splits (designed, not yet built).** When a case is split, the new child case inherits only the embargo ([ADR-0125](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0125-case-split-child-case-inherits-the-embargo-only.md)).

### Joining, leaving, and closing have defined edges

- **Joining.** An invited party is first seated as an inactive participant with only a case summary. It sees the full case only after it accepts ([ADR-0114](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0114-joining-a-case-stub-invite-inert-participant.md)).
- **Leaving.** Every way of leaving a case goes through one leave-case action ([ADR-0145](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0145-a-case-is-left-through-the-leave-case-trigger-whose-actor-runs-its-pre-close-step-first.md)).
- **After closure.** Once a case is fully closed, late messages are dropped. The one exception is a late request to leave, which can be answered ([ADR-0131](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0131-post-close-traffic-is-dropped-and-only-a-late-leave-may-be-answered.md)).

### Message content rules

- **Never invent values.** An implementation never sends a value it doesn't know. A party known only by its address travels as a minimal reference (address and type) rather than with invented profile details ([ADR-0159](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0159-an-actor-known-only-by-uri-travels-as-an-id-and-type-reference.md)).
- **Refer to a case; don't copy it.** A participant's message about a case names the case instead of embedding a full copy of it ([ADR-0165](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0165-a-participants-act-on-a-case-names-the-case-and-never-carries-it.md)).
- **Signing.** Actors will sign message content with keys seeded for the prototype ([ADR-0164](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0164-actors-sign-content-with-object-level-proofs-from-seeded-keys.md)). This is designed and tracked as known-failing tests; it is not built yet.

### The requirements themselves were audited

Every protocol requirement was reviewed, and the review did three things:

- **Classified it.** Each requirement is now either a protocol obligation that every implementation must meet, or a "foundation" rule inherited from ActivityStreams, ActivityPub, or HTTP.
- **Gave it a reason.** Each requirement now carries a written rationale.
- **Split compound ones.** Requirements that bundled several obligations were split into one obligation each.

**What we learned:** some requirements that called for full objects inside messages only described a shortcut the prototype had taken, so they were reclassified ([PR #4662](https://github.com/CERTCC/Vultron/pull/4662)).

**You can now:** see, for any protocol rule, whether it is a Vultron obligation or an inherited one, and why it exists.

## The Documentation Site: New Content and Organization

### Organized by reader, not document type

In September the site's top level was organized by document type: Start Here, Tutorials, Explanation, How-to Guides, Reference. In October it was reorganized by subject and reader ([ADR-0136](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0136-organize-the-site-top-level-by-subject-and-reader-not-diataxis-type.md), [PR #5176](https://github.com/CERTCC/Vultron/pull/5176)):

- **How Vultron Works:** a new overview page, background, the case lifecycle, and the glossary.
- **Coordinate Cases:** for CVD program staff.
- **Implement the Protocol:** the specification, messages, and conformance.
- **Reference Implementation:** demos and architecture.
- **Research:** measuring CVD and other uses of Vultron.
- **Project:** project-level pages such as versioning.

Pages can also be reached through guided reading paths with previous/next links ([PR #5085](https://github.com/CERTCC/Vultron/pull/5085)), and a "Look Something Up" page gives returning readers one cross-tabulated index of the reference pages ([PR #5251](https://github.com/CERTCC/Vultron/pull/5251)).

### The Protocol Specification became a standards-style document

- **Separate pages.** The single long [Protocol Specification](https://github.com/CERTCC/Vultron/blob/main/docs/reference/vultron-spec/index.md) page was split into numbered sections plus seven annexes ([PR #4088](https://github.com/CERTCC/Vultron/pull/4088)). The annexes cover single-vendor and multi-party walkthroughs, notation, case histories, ActivityPub, behavior trees, and capability shapes.
- **Requirements catalog.** A new [§14 Requirements Catalog](https://github.com/CERTCC/Vultron/blob/main/docs/reference/vultron-spec/requirements/index.md) gives every requirement a single anchor, grouped into eight themed pages ([PR #5514](https://github.com/CERTCC/Vultron/pull/5514)).
- **Generated from one source.** The normative text is rendered from the same requirement files the tests check against, so the published specification and the tested requirements come from one source ([ADR-0147](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0147-the-protocol-specification-renders-its-normative-text-from-the-yaml-requirements.md)). Four specification pages were reconciled into that form.
- **Normative or not.** A banner marks exactly which pages are normative (binding) ([PR #5086](https://github.com/CERTCC/Vultron/pull/5086)).
- **Notation and open questions.** A new [notation annex](https://github.com/CERTCC/Vultron/blob/main/docs/reference/vultron-spec/annex-c-notation.md) defines one way of writing message examples, used on every page ([PR #5153](https://github.com/CERTCC/Vultron/pull/5153)). A new page lists the specification's [open questions](https://github.com/CERTCC/Vultron/blob/main/docs/reference/vultron-spec/open-questions.md).

### Messages are documented by "occasion"

The messages reference is now organized around **occasions**: each situation in which a message is sent, with a generated table of who sends it, to whom, and in what situation ([ADR-0128](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0128-message-vocabulary-docs-are-projections-of-the-semantic-registry.md), [PR #4572](https://github.com/CERTCC/Vultron/pull/4572), [PR #4720](https://github.com/CERTCC/Vultron/pull/4720)). How-to guides embed the occasions they use, and reference sections list where each one appears ([PR #4579](https://github.com/CERTCC/Vultron/pull/4579)). A proposed decision makes the occasion the specification's basic unit of normative statements about messages ([ADR-0158](https://github.com/CERTCC/Vultron/blob/main/docs/adr/0158-the-occasion-is-the-specifications-message-unit-and-case-coordination-is-its-own-section.md)).

**You can now:** start from "I'm the vendor and I want to propose an embargo" and find the exact message to send and who receives it, instead of working backward from the message vocabulary.

### New and rewritten content

- **Decide Who Owns a Case.** A new how-to guide on when to submit a report, create a case, or transfer ownership ([PR #5273](https://github.com/CERTCC/Vultron/pull/5273)).
- **CSAF 2.1 crosswalk.** A five-page mapping and gap analysis against CSAF 2.1 (the OASIS standard for machine-readable security advisories), with proposals for closing the gaps ([PR #5138](https://github.com/CERTCC/Vultron/pull/5138)).
- **Nine new user stories** on what sets Vultron apart, such as per-version embargo consent, a shared tamper-evident ledger, keeping cases consistent when messages arrive out of order, explicit answers to every request, and testing conformance claims ([PR #5425](https://github.com/CERTCC/Vultron/pull/5425)).
- **Measuring CVD** was restructured to describe today's model first, with the original model kept as background ([PR #5144](https://github.com/CERTCC/Vultron/pull/5144)).
- **Simplified wording.** The embargo, case-management, and report-management pages were rewritten in simplified technical English, a controlled plain-language standard ([PR #5214](https://github.com/CERTCC/Vultron/pull/5214), [PR #5237](https://github.com/CERTCC/Vultron/pull/5237)).

## The Reference Implementation: What You Can Run Now

[v2026.10.0](https://github.com/CERTCC/Vultron/releases/tag/v2026.10.0) (October 23) is the first release since v2024.4.3. The earlier release was a written model plus a simulation. This one is a runnable reference implementation in which reporters, vendors, and coordinators exchange standard social-web messages (ActivityStreams 2.0) over HTTP. The release notes say plainly that it is not for production use.

Compared with September, you can now run:

- **Embargo negotiation across three and four parties.** New scenarios cover a reporter proposing terms with the report, a reporter–coordinator–vendor negotiation, and a two-vendor case with an embargo revision ([PR #3995](https://github.com/CERTCC/Vultron/pull/3995), [PR #4306](https://github.com/CERTCC/Vultron/pull/4306), [PR #4329](https://github.com/CERTCC/Vultron/pull/4329)). All of them run against a dedicated case-manager container that holds the authoritative record ([PR #4539](https://github.com/CERTCC/Vultron/pull/4539)).
- **New case actions:** withdrawing from an embargo, removing and reinstating participants, transferring case ownership (offer, reject, withdraw, deadline), and a single leave-case action. Each one is implemented as specified in the decisions above.
- **Replaying a case in a browser.** A contributor's interactive demo UI was merged ([PR #3754](https://github.com/CERTCC/Vultron/pull/3754)). Its Log Replay mode uses repeatable recordings produced by the real scenario code, and a daily job on the main branch checks those recordings for staleness ([PR #5336](https://github.com/CERTCC/Vultron/pull/5336)). **What we learned:** recording every scenario twice exposed two sources of run-to-run variation, and both were removed for recordings.
- **Clearer refusals.** About 100 targeted fixes closed specific gaps in how received messages are checked. A refused message now gets a standard Reject, and one that fails on an internal error gets a separate fault reply. These are individual fixes, not a claim that every malformed input is caught.

**In progress:** building scenarios from a shared opening sequence began on October 30–31 ([PR #5588](https://github.com/CERTCC/Vultron/pull/5588), [PR #5594](https://github.com/CERTCC/Vultron/pull/5594)), and most scenarios have not been converted yet.
