## Context

SR-11 added bidirectional spec-to-story traceability. During the 2026-08-25 mapping pass,
~20 protocol MUST specs covering state machine formal properties could not be mapped to any
existing user story.

These specs define correctness invariants — forbidden CS states, forced-successor rules,
duration arithmetic, timezone handling, the single-writer axiom — that protocol authors and
auditors need to be able to trace to stakeholder intent.

## Specs needing story coverage

**CS state machine formal properties** (`specs/cs-behavior.yaml`):

- `CSB-17-001` — exactly 32 compound CS states (4×VFD × 8×PXA)
- `CSB-17-003` — vP and pX are ephemeral states
- `CSB-17-006` — vF (fix ready while vendor unaware) is forbidden
- `CSB-17-007` — fD (fix deployed but never ready) is forbidden
- `CSB-17-009` — from vP, next event MUST be V (forced successor)
- `CSB-17-012` — from pX, next event MUST be P (forced successor)
- `CSB-17-013` — any other event from an ephemeral state is rejected

**State machine implementation correctness** (`specs/state-machine.yaml`):

- `SM-01-003` — use enum values, not raw strings, in transitions
- `SM-03-003` — all (source, dest) transition pairs must be verified

**Architecture and ordering** (`specs/vultron-protocol-spec.yaml`):

- `VP-17-001` — single-writer axiom: CaseActor is the sole writer to case state

**Duration validation and arithmetic** (`specs/duration.yaml`):

- `DUR-04-001` — reject disallowed units (Y, date-part M, W)
- `DUR-04-002` — reject malformed ISO 8601 strings
- `DUR-04-003` — reject empty durations (`P` or `PT`)
- `DUR-04-004` — require at least one component
- `DUR-05-002` — timedelta → ISO 8601 serialization
- `DUR-06-002` — `end = start + duration` arithmetic formula
- `DUR-06-003` — RFC 3339 timestamps for interval composition

**Embargo timing** (`specs/case-management.yaml`):

- `CM-28-006` — normalize Invite `end_time` to UTC; reject naive datetimes
- `CM-28-007` — lazy evaluation of embargo invite expiry

**State transition guards** (`specs/case-management.yaml`):

- `CM-04-005` — validate transition against current state before persisting
- `CM-04-009` — at most one field updated per accept event

**Embargo guard** (`specs/em-behavior.yaml`):

- `EMB-14-002` — EmbargoExitPolicyGuard evaluator call-out in BT

## Suggested story framing

- *As a protocol author, I want the CS state machine's formal invariants — forbidden
  states, forced successors, ephemeral transitions — to be traceable to a stakeholder
  need, so that future implementers understand why these constraints exist.*
- *As a Participant, I want embargo deadlines and duration values to be validated and
  computed using a well-defined, timezone-aware arithmetic, so that embargo expiry is
  unambiguous across all participants.*
- *As a Participant, I want the guarantee that only one authoritative writer can update
  case state at a time, so that concurrent operations cannot produce inconsistent outcomes.*
