## Summary

Make each inbound message one record whose stage field moves through a fixed order
of questions: *is this for me?*, *have I seen it?*, *which path am I on for this case,
and does that path handle this message type?*, *is the sender entitled?*, then the
handling tree. The receiver's role is checked once per message through one shared
`has_role` predicate, and only the CASE_MANAGER role picks the path (manager,
participant replica, or no case yet). Arrivals wait in a holding stage and leave it
only on their final outcome: applied messages go to the long-term archive, refused
ones leave a receipt stub.

## Motivation

Received handlers decide "am I this case's CASE_MANAGER?" in about ten different ways:

- the factory's `CaseManagerGate` around `manager_effects` (~30 trees) and its
  inverse `create_participant_replica_gated_tree`;
- CASE_MANAGER-gated precondition guards inside node modules;
- `SenderRule` arms that branch on the receiver (`at_case_manager` / `at_participant`);
- the `ReplicaEmitExemption` and `AddresseeExemption` registries;
- `DiversionGate.CASE_MANAGER` / `RECEIVER`;
- post-run handler checks such as `not_case_manager(tree)`, which reads "not the
  manager" from *any* failed `CheckIsCaseManagerNode` in the tree;
- hand-rolled gates (`sync/announce_tree.py`, `CheckFullCaseReplyNode`);
- inline `resolve_case_manager_id(...) == actor_id` comparisons;
- `SenderIsCaseOwnerNode` reused to ask about the receiver or invitee.

Each received tree also carries "not my job" skip arms. The wrong-role verdict is
inconsistent across handlers (#5010), and #4851 and #4970 are role
refusals that fired wrongly. All of this follows from asking the role question late
and in many places.

The ordering is also the wrong way round. Intake archives every arrival before the
addressee, path or sender checks, so a message that is not for the receiver, and that
it will never act on, is stored permanently (CLP-10-017/018). Asked in the right order,
an early answer makes the later steps unnecessary.

These don't hold the idea back:

- **Role belongs to (actor, case), not to the actor.** An actor can manage case Y
  while being a plain participant in case X, and anyone can receive a report that
  starts a new case. So the branch can't be fixed at actor startup, but it can be
  decided once per message.
- **The Case Owner is not a path.** Like every participant it holds a replica and sends
  its changes through the CASE_MANAGER. Owner, vendor, deployer and every other role
  are permission rules inside a path, checked with the same `has_role` predicate. A new
  role adds permission rules, never a new path.

## Rough Approach

1. **Order of questions.** Each answer can end the run:
   1. Addressed to me? No → REFUSED (HP-01-005).
   2. Seen before? Yes → SKIPPED (duplicate).
   3. Which path, by the CASE_MANAGER role in this case (manager / participant replica /
      no case yet), and does this message type declare a branch for that path? No →
      REFUSED with "not the CASE_MANAGER of case …", composed once by the factory.
      "No case yet" either waits for the case (case-scoped types, as the defer check
      does today) or takes the no-case path (types that start a case: reports, case
      proposals, the first `Create(VulnerabilityCase)`).
   4. Case open to external writes, sender entitled?
   5. The handling tree: precondition guards → commit → effects.

   Message types that do real work on both paths declare a manager branch and a
   participant branch, and the shared tree builder forks once, after the door stages.
   That covers `Invite`/`Remove(EmbargoEvent)`, role and ownership offers,
   `Add(CaseStatus)`, `Announce`/`Reject(CaseLedgerEntry)` and the case invites.
2. **One shared role predicate.** `has_role(actor, case, role) -> bool` is checked fresh
   for each message, because roles change during a case. It is a cheap read of the
   actor's own replica, like today's `CheckIsCaseManagerNode`, and it is the only
   sanctioned way to ask.
3. **One record per message, with a stage field.**
   `received → door-checked → [waiting] → handled → final outcome`. Each stage has one
   way in and two ways out: move on, or leave with an outcome. The record rests only
   where time can pass: waiting for its case (this absorbs `VultronPendingCaseInbox`)
   or waiting for a local decision. At its final outcome:
   - applied → long-term archive;
   - refused → a **receipt stub** (sender, message id, time, reason, hash of the body),
     so "receipt is a fact" still holds without keeping content that was never the
     receiver's;
   - duplicate → dropped, because the original is already recorded.

   A message leaves holding only on its final outcome, so a crash mid-run leaves it in
   holding to be re-run. The handling tree has to tolerate that re-run, which the
   existing once-per-act commit and derived-id sends are meant to provide
   (SYNC-09-002, OX-06-002). That needs verifying for every tree.
4. **Split points around the handling tree only.** Stage boundaries are arrival → doors
   → waiting → handling tree → outcome. A stage reads only the record and the store,
   never what an earlier stage left in memory, and an architecture test can pin that.
   The handling tree itself stays one unit (ADR-0135), keeping its blackboard. No new
   queues or workers now. The rule keeps the option open to run stages as separate
   queues or functions later (for example AWS Lambda).
5. **ADR first.** This changes ADR-0111 (intake is the first stage and archives every
   arrival) and CLP-10-017/018/019, and it has to fit ADR-0149 / #4943 (the archive is
   the verbatim received body). The ADR should place the holding stage and the receipt
   stub relative to that archive shape.

Open questions for the ADR:

- How do duplicate detection (step 2) and the receipt stub interact? Does a re-delivery
  of a refused message match its stub and count as a duplicate, or get refused again?
- `Offer(Report)` keeps the report and the Offer even when the receiver declines to
  create a case (CM-15-002). Is that the no-case path's applied outcome, or still a
  registered exemption?
- Which received trees today assume intake already wrote the archive before their
  guards run, and would have to read from the holding record instead?
