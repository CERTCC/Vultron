## Context

SR-11 added bidirectional spec-to-story traceability. During the 2026-08-25 mapping pass,
~15 protocol MUST specs covering distributed case state consistency could not be mapped to
any existing user story.

These specs define the guarantees that make a replicated, append-only case ledger
trustworthy — ordering constraints, rehydration pipeline, object identity, and per-actor
isolation. A Coordinator or Vendor needs these properties even if they never see the
internals.

## Specs needing story coverage

**Sync and replication** (`specs/sync-ledger-replication.yaml`):

- `SYNC-01-005` — forward-compatibility with future Merkle Tree implementation
- `SYNC-05-003` — documented default retry/backoff values

**Participant case replica** (`specs/participant-case-replica.yaml`):

- `PCR-06-004` — pending-activity queue keyed by composite actor-ID + case-ID
- `PCR-08-006` — fail-fast when CaseActor is not resolvable (BT emit node)
- `PCR-08-016` — unit/integration test coverage for replica lifecycle

**Object identity** (`specs/object-ids.yaml`):

- `OID-02-001` — full URI as primary key in DataLayer
- `OID-02-002` — `object_to_record()` preserves full URI
- `OID-02-003` — `record_to_object()` reconstructs from stored URI

**Ledger ordering** (`specs/case-management.yaml`):

- `CM-16-010` — ledger entries committed AFTER messages are queued for delivery
- `CM-17-006` — CaseLedgerEntry for Invite committed before Invite is delivered

**Vocabulary rehydration pipeline** (`specs/vocabulary-model.yaml`):

- `VM-06-001` — rehydration precedes semantic extraction
- `VM-06-002` — DataLayer parameter passing in `rehydrate()`
- `VM-06-003` — recursive rehydration depth limit
- `VM-06-004` — graceful handling of unresolvable URI references
- `VM-06-005` — error propagation when vocabulary lookup fails

**Case actor identity** (`specs/case-management.yaml`):

- `CM-02-003` — CaseActor persists until VulnerabilityCase is closed
- `CM-02-010` — CaseActor and case owner MUST have distinct actor identities

## Suggested story framing

- *As a Coordinator, I want the case ledger to be an append-only, tamper-evident record
  of all case events, so that I can audit the full history of a CVD case and resolve
  disputes about what happened and when.*
- *As a Participant, I want all incoming activities to be fully resolved (rehydrated) from
  their URI references before being processed, so that case state is always based on
  complete, authoritative data rather than opaque identifiers.*
- *As a Participant, I want case actors and case owners to have distinct, stable identities,
  so that the provenance of every case event is unambiguous even across deployments.*
