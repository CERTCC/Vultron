## Context

SR-11 added bidirectional spec-to-story traceability. During the 2026-08-25 mapping pass,
~25 protocol MUST specs in the wire-format / response-encoding area could not be mapped to
any of the 111 existing user stories (`story_2022_001`–`story_2022_111`).

These specs describe exact AS2 encoding rules, response-activity structure, and
serialization formats that an implementer building a Vultron-compatible peer needs to satisfy.
They are protocol-level requirements, not implementation details — they just lack the
stakeholder-voice framing a user story provides.

## Specs needing story coverage

**Response format encoding** (`specs/response-format.yaml`):

- `RF-02-002` through `RF-02-005` — Accept activity `object` encoding
- `RF-03-003`, `RF-03-004` — Reject response encoding
- `RF-04-003`, `RF-04-004` — TentativeReject encoding
- `RF-08-002` — `inReplyTo` constraint enforcement
- `RF-09-001` — idempotency of response generation

**Vultron AS2 mapping edge cases** (`specs/vultron-as2-mapping.yaml`):

- `VAM-01-001` — registry completeness (all semantics have wire patterns)
- `VAM-01-003` — pattern ordering (most-specific first)
- `VAM-01-005` — full rehydration before pattern matching
- `VAM-01-006`, `VAM-01-007`, `VAM-01-008`, `VAM-01-009` — fallback/UNKNOWN rules
- `VAM-09-001` — unmatched activity → UNKNOWN

**Non-dispatching message semantics** (`specs/message-semantics-mapping.yaml`):

- `MSM-01-007` — RE (Report Management Error): no dispatch
- `MSM-02-008` — EE (Embargo Management Error): no dispatch
- `MSM-02-009` — EK (Embargo Management Acknowledgment): no dispatch
- `MSM-03-007` — CE (Case State Error): no dispatch
- `MSM-03-008` — CK (Case State Acknowledgment): no dispatch

**Serialization formats**:

- `CS-07-003` (`specs/code-style.yaml`) — datetime RFC 3339/ISO 8601 wire format
- `DUR-01-002` (`specs/duration.yaml`) — duration serialized as JSON string
- `DUR-02-001` — allowed grammar units (D, H, M, S only)

## Suggested story framing

- *As an implementer building a Vultron-compatible peer, I want the protocol to fully
  specify how response activities (Accept, Reject, TentativeReject) must be encoded on
  the wire, so I can implement them correctly without ambiguity.*
- *As an implementer, I want the wire mapping of non-dispatching messages (acknowledgments,
  error signals) to be specified, so I know which AS2 activities carry them and how to
  handle them.*
- *As an implementer, I want datetime and duration values to have a canonical wire
  serialization format, so that interoperability does not depend on implementation-specific
  choices.*
