## Summary

A demo scenario exercising the parent/child/sibling case relationship model. One case is discovered to involve two separate but related vulnerabilities affecting different vendors; the coordinator splits it into two child cases. Alternatively, two independent cases tracking the same underlying vulnerability are merged into a single parent case.

## Motivation

Case split and merge are defined in the data model (parent/child/sibling cases in the glossary) but never exercised in demos. This would clarify the semantics of case hierarchy and test the CaseActor's case-relationship management.

## Rough Approach

Split: start with an FCV case for V1's product; C finds V2 is also affected; C creates a child case linked to the parent; V2 is invited to the child only; both cases run to closure.

Merge: F1 reports to C1 and F2 to C2 for the same vulnerability; C1 and C2 agree to merge; participants from both are consolidated under the parent.

## Acceptance Criteria

- Parent/child relationship is persisted in CaseActor's DataLayer
- Participants of a child case cannot access parent case data
- Merged case preserves both participant lists
- At least the split scenario runs deterministically

**Processed**: 2026-10-06 — implementation tracked in #4241, #4242, #4243, #4244. The child case inherits the embargo only; the split demo is a contrived mechanism demo; the merge demo follows ADR-0105 (invitation, not consolidation). Docs PR: <https://github.com/CERTCC/Vultron/pull/4246>.
