## Problem

Scenario tests rebuild a whole multi-actor case from nothing for every test.

For example, `test_the_managers_withdrawal_declines_the_revision_it_agreed_to` in `test/core/use_cases/received/test_embargo_proposal_answer_copy.py` takes these steps:

1. It builds a fresh `LedgerNetwork`.
2. A participant proposes a revision.
3. The CASE_MANAGER accepts it.
4. The CASE_MANAGER withdraws.

Only the last step is under test. In a profiled run the test ran its behavior tree 31 times. Afterwards, the autouse rebuild check (`_every_network_rebuilds_from_its_ledger`) replays the whole ledger again.

The slowest tests in that file take 3–6 seconds each, over the TB-12-003 budget of 5 seconds. Sibling tests in the same file rebuild the same first steps.

This is the scenario tree's shared-prefix idea, applied to tests. Many tests share the same steps up to a branch point and differ only in the act after it.

## Idea

Name the case states that many tests start from, for example "participant proposed a revision" or "CASE_MANAGER has agreed". Build each one once per module or session, and give every test its own copy.

Each test still starts from fresh state of its own (TB-06-001, TB-06-003). It just doesn't replay the steps to get there.

## Decisions needed

1. **The copy mechanism.** `SqliteDataLayer.clone_for_actor` exists, and SQLite can copy a whole in-memory database (`sqlite3.Connection.backup`). Neither has been checked for copying a full store, including the actor locks, clock patching, and the `NETWORKS` registry the rebuild check reads.
2. **How the rebuild check treats a copied network.** It could replay from the copy's seed, or from the original's. It could also skip starting points that were already checked once.
3. **Which states become starting points, and where they live.** One option is a shared module next to `_ledger_network.py`. Another is the branch points of the demo scenario tree, if #4733 settles a composition model both could use.
4. **The pilot file and the success measure.** For example: `test_embargo_proposal_answer_copy.py`, wall time before and after, and no test over the TB-12-003 budget.

Outcome of the planning interview: tests start from named points on the demo
scenario tree (one map for demos and tests), not a separate test-only tree.
Each point is built once per session with the recordings' seeding and copied
per test with SQLite `backup`; each step is tested once, and the rebuild check
proves each point once and replays only a test's own entries. Profiling showed
one received act rereads the case 90 times (743 reads of 73 records) and the
outbox per queued Announce, so making one act cheap (#5344) comes first.
