## Summary

This prototype attaches a case status, a participant status and a participant record with a single `Add` that carries the object inline, and carries a proposed `EmbargoEvent` inline on the `Invite`. It refuses a received `Create` of any of these objects as an unrecognized activity (VAM-01-010, #4598). That is a decision for this implementation only. Whether the **protocol** should allow other forms is still open.

## Options

1. **Single `Add` only.** The protocol states the inline `Add` (or the `Invite`, for an embargo proposal) as the only form. A separate `Create` of these objects is not a protocol message.
2. **`Create` then `Add`.** A participant may mint the object with `Create` and attach it later with an `Add` that references it. This is how ActivityStreams allows it in general. Support would need:
   - its own committed ledger entry for each `Create`, since it changes the case file (CLP-07-013);
   - a replica apply step or a declared no-replica-effect row for that entry (RSH-08-004);
   - an `Add` that resolves a reference to the stored object.
3. **`Create` with a case `context` attaches the object.** One message, the way `Create(Note)` with a case `context` already attaches a note. Support would need its own ledger entry and replica apply step for each `Create`, the same as option 2, but no `Add`-by-reference.

## Notes

- These objects have no meaning apart from their attachment: a participant status declares the sender's own state, an embargo proposal travels on the `Invite`, and participant records are created by the CASE_MANAGER. That argues for option 1. A note is different: it is content that can stand on its own.
- `docs/topics/future_work/_oq-create-then-add.md` records the question on the Open Questions and Activity Vocabulary Design pages.
