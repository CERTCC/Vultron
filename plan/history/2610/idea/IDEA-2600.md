## Context

SR-11 added bidirectional spec-to-story traceability. During the 2026-08-25 mapping pass,
~25 protocol MUST specs covering semantic extraction, structured logging, and API
discoverability could not be mapped to any existing user story.

These specs exist to make Vultron's protocol machine-readable and observable — enabling
automated agents, conformance tooling, and operators to consume and analyze the protocol
programmatically. They are protocol-level requirements, but the 111 existing stories don't
include a tool-author or automated-agent persona.

## Specs needing story coverage

**Semantic extraction engine** (`specs/semantic-extraction.yaml`) — all 21:

- `SE-01-001` through `SE-01-004` — pattern matching, rehydration, dead-letter behavior
- `SE-02-001` through `SE-02-003` — semantics assignment, first-match-wins, UNKNOWN fallback
- `SE-03-001` through `SE-03-003` — registry completeness, ordering, discrimination
- `SE-04-001` through `SE-04-004` — WARNING log on unrecognized activity, dead-letter schema,
  HTTP 422 for synchronous unresolvable path
- `SE-05-001`, `SE-05-002` — pattern-to-enum and pattern-to-use-case-map consistency
- `SE-08-001`, `SE-08-002`, `SE-08-004`, `SE-08-005` — target discriminator, deprecation record

**Structured logging with correlation** (`specs/structured-logging.yaml`):

- `SL-02-001` — log entries include `activity_id` correlation field
- `SL-02-002` — log entries include `actor_id` correlation field

**Agentic readiness / OpenAPI** (`specs/agentic-readiness.yaml`):

- `AR-07-003` — action-rules endpoint registered in OpenAPI schema
- `AR-10-002` — HTTP 404 when actor is not found (actor profile endpoint)

**Inbox observability** (`specs/inbox-endpoint.yaml`):

- `IE-09-001` — structured INFO-level logging of all requests

## Suggested story framing

- *As a tool author building a Vultron conformance test suite, I want the semantic
  dispatch engine to have a well-specified pattern registry — completeness checks,
  ordering rules, dead-letter handling — so I can verify that an implementation routes
  every message to the right handler.*
- *As an operator monitoring a Vultron deployment, I want every log entry to include
  `activity_id` and `actor_id` correlation fields, so I can trace any protocol event
  through the system without grepping for context.*
- *As an automated agent consuming the Vultron API, I want all endpoints to be
  discoverable via the registered OpenAPI schema, so I can generate a client without
  reading implementation source code.*

## Note

The semantic extraction specs (`SE-*`) describe an NLP/pattern-matching pipeline that
classifies incoming AS2 activities into protocol semantics. This is invisible to human
Participants but is what makes the protocol machine-processable. A "tool author" or
"automated agent" persona may be needed in the user story catalog for this cluster.
