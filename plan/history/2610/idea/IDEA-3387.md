## Design idea

Decide once whether a `specs/*.yaml` file's `version` field MUST be bumped when its requirements change, then enforce the answer in `spec-lint` instead of leaving it to per-PR judgment. The issue weighed three positions: semver-on-requirements, bump-on-any-change, or retiring the field's implied contract.

**Processed**: 2026-10-05 — no implementation needed. The question was overtaken by events: commit `a264052e7` removed the per-file `version` field entirely. SR-01-003 now says a spec file MUST NOT have a top-level `version` field (rationale: a hand-maintained version had no rule for when it changed and no check that it did; the release tag pins spec content and the requirement ID is the citation address, ADR-0106). SR-02-013 keeps `SpecFile` at `extra="forbid"`, so `spec-lint` rejects any file that declares one, with no git access needed. No file in `specs/` carries a `version:` line. Closed as already resolved; no docs changes, no implementation issues.
