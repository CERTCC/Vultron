## Summary

Nothing records, per message, the difference between what the protocol allows and what this implementation sends.
For example, a note can reach a case as `Create(Note)` whose note's `context` is the case, or as `Add(Note, target=Case)`. A receiver must accept both, and this implementation's add-note trigger sends one of them (#4549).
Without a place to say that, the implementation's habits enter the reader docs as protocol rules.
The `create_note` occasion text said "It precedes the Add that attaches it", and the FV demo protocol page and the status-updates how-to told readers to send Create, then Add. All three describe what our trigger did, but they read as what the protocol requires.

## What exists

- Spec `kind` (ADR-0038): `protocol` vs. `project` tags each requirement. This works at the requirement level only, not for a message's alternative forms.
- Capability sets (conformance §12.2): these say which groups of obligations software takes on. They are too coarse to say which wire form gets sent.
- The glossary's "Reference Implementation Vocabulary" section: it separates names, not behaviors.
- Semantic-registry occasions (ADR-0128): these describe a sender's situation, but have no field for "a receiver also accepts this form" vs. "this implementation sends this form".

## Directions to weigh

- A sends/accepts distinction on occasions (or on `SemanticEntry`), rendered on the message reference pages.
- A convention that pairs a `kind: protocol` receiver-acceptance requirement with a `kind: project` emission requirement whenever a message has alternative forms.
- A conformance-chapter convention listing alternative forms and which ones the reference implementation emits.

## Reference

Surfaced while planning #4545; first instance fixed in #4549.

## Decision

- A per-message "the protocol allows these forms, this implementation sends that one" marker was weighed and rejected (MS-18-002).
- When ActivityStreams allows several wire forms for one act, the `protocol` requirement names exactly one form. The other forms are recorded as deferred alternatives in an open question (MS-18-001).
- Notes are attached only by `Add(Note)` with the case as `target` (ADR-0137, amended in place), and `Create(Note)` is retired.
- #4692 was amended to keep the open question, and #4678 was closed as superseded.
