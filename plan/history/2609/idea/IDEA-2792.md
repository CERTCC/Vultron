## Summary

Enrich the public docs/topics/ Explanation quadrant with protocol messaging
semantics content drawn from implementation notes. The core concept —
that ActivityStreams activities are state-change notifications, not commands,
and that objects may be stub-only for selective disclosure — is fundamental
for any external implementer building a Vultron-compatible node.

## Motivation

External implementers (any language) need to understand *why* the protocol
works the way it does before they can implement it correctly. This concept
is captured in contributor-facing notes but is absent from the public
Explanation quadrant.

## Scope

Source notes:

- notes/activitystreams-semantics.md — Activities as state-change notifications; inbound/outbound semantics; Accept/Reject rules
- notes/stub-objects.md — Stub objects, selective disclosure, and object verbosity tradeoffs

These may produce one new page, two pages, or sections on existing pages — the deep-pass decides.

## Acceptance Criteria

- AC-1: Read both source notes files; check existing docs/topics/ for overlap
- AC-2: Decide: new page / enrich existing / merge (document the decision)
- AC-3: Strip Python-specific content (class names, Pydantic patterns, pitfall lists)
- AC-4: Keep design rationale, "why this protocol behavior", alternatives considered
- AC-5: Add framing accessible to external implementers unfamiliar with this codebase
- AC-6: Run /simplified-technical-english on any new or modified page
