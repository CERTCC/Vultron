## Original idea (#3286)

Add additional pages to the `docs/topics/future_work/` section (created in #3285)
covering open design areas not addressed in the federation issue: full ActivityPub
server implementation, peer-to-peer encryption, message signing, and distributed
ledger approaches.

Scope as filed: identify relevant notes files and GitHub issues for each topic;
determine which have enough settled design content for a Future Work page vs. are
too speculative; write pages for approved topics; document reasoning for any
skipped; add pages to the Future Work nav.

Source: #2799. Related: #3285 (creates the Future Work section).

## Outcome

**Processed**: 2026-09-17 — implemented together with #3285 in a single PR.

The planning interview reframed all four topics. None is "too speculative to
document" and none is settled design; each is a capability the prototype has not
built, which is not the same as a capability the project has ruled out. So instead
of four pages, each topic became a short open-question entry that states the
current state, what design exists, and where it is tracked — the shape the
existing `docs/reference/vultron-spec/_oq-*.md` fragments already use.

Topic disposition:

- **ActivityPub depth** → `_oq-activitypub-depth.md`, tracked by #2068 (which
  already owned "design and build a full ActivityPub service"; an earlier read
  that nothing tracked this was wrong)
- **Actor discoverability** → separated from ActivityPub depth at the maintainer's
  direction, and merged into `_oq-actor-discovery.md` (which absorbed the
  `_oq-directory-service` entry #3285 planned), tracked by #1189

  the same key material; tracked by epic #1156, with #509, #892, #1163, #2841
- **Distributed ledger** → `_oq-distributed-ledger.md`, tracked by epic #1158

## Requirement change this surfaced

`specs/encryption.yaml` ENC-01 required "one key pair per case, bound to the
CaseActor for that case's lifetime", with a rationale asserting that "the 1:1
case-actor-to-case assumption holds". Key material binds to an **actor identity**,
not to a case: an actor enacting `CVDRole.CASE_MANAGER` for several cases uses one
key pair for all of them, and per-case key separation is a consequence of
provisioning one CASE_MANAGER actor per case — a deployment-topology choice, not a
key-binding rule.

The maintainer chose to fix it in this PR rather than file it. ENC-01/ENC-02 were
amended in place (no new requirement IDs, so the protocol-coverage ratchet stayed
neutral) and the file's twelve `CaseActor` references were cleared per ADR-0088.
Whether a production deployment should provision one CASE_MANAGER actor per case
remains open, and is now stated as such in `notes/encryption.md` and on the
Future Work page.

Follow-up filed: #3342 — the same ADR-0088 sweep over the rest of `specs/`
(#3306 did `notes/`; `specs/` was never done).
