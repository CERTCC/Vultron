## Summary

Identify all versionable components of the Vultron protocol and its implementation, then design a coherent strategy for versioning and maintaining them — including what GitHub Releases mean in a multi-component monorepo.

## Motivation

The Vultron project contains multiple distinct artifacts that may evolve at different paces: the protocol vocabulary (verbs, nouns, semantic mappings), behavioral specifications (use-case and trigger logic), the Python library, demos, documentation/website, and possibly the repository schema itself. Without an explicit versioning strategy, consumers cannot know what changed between releases, which components are stable vs. experimental, or how to express compatibility constraints.

GitHub Releases add a further wrinkle: in a monorepo with components moving at different cadences, a single release tag conflates unrelated changes and makes SemVer semantics ambiguous. This applies especially as the project engages with external standards bodies (FIRST, CSAF, etc.) that may want to reference specific stable versions of protocol artifacts.

## Rough Approach

1. Enumerate the versionable things — vocabulary, behaviors, Python package, demos, docs/website, repository structure, possibly others — and characterize each one's stability, ownership, and expected rate of change.
2. Decide which components share a version line vs. have independent versions, and what the coupling contract is between them.
3. Determine what a GitHub Release means in this context: one unified release? Multiple per-component tags? A release manifest?
4. Produce an ADR (or set of ADRs) capturing the decisions, and update `CONTRIBUTING.md` / `docs/` accordingly.

**Processed**: 2026-09-24. Planned via grill-me. Outcome: versioning splits into two jobs.

- **Naming a release** — the CalVer tag names the whole-repo snapshot and makes no compatibility claim. There is one GitHub Release per tag, not Pre-release. Tracked in #3553 (ADR-0006 amendment).
- **Naming a format** — each machine-facing interface has an independent version, bumped only on an incompatible change: the wire format (in the context URL), the ledger hash format (per case, at genesis), the HTTP API (`/api/v2` major), and stored data (a marker, refuse on mismatch, no migrations). Config gets strict validation instead of a version. Protocol behavior gets a new-requirement-ID rule instead of a number. `/version` reports compatibility, never the exact build. Tracked in #3554 (versioning ADR, rewritten).
- The page/artifact maturity manifest is dropped (YAGNI): every interface is experimental. #3555 shrinks to the scenario-page correctness check.
