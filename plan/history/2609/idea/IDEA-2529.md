## Idea

Create a page (or short section) aimed at a developer asking: "I want to build something that speaks Vultron — what does the implementation structure look like, and where do I start?"

## Context

`howto/process_implementation.md` was written as aspirational guidance before the current architecture existed. It should eventually be replaced with something accurate and useful, but the right form needs refinement:

- Is this **How-to** ("here are the steps to implement an actor")? That requires a concrete, reproducible path.
- Is this **Explanation** ("here is how the reference implementation is structured and why")? That maps the hexagonal architecture, ports/adapters, BT orchestration, inbox pipeline, and outbox to what an implementer needs to understand.
- Or is it both — an Explanation of the structure followed by a How-to that points at the reference implementation as a starting point?

## What the content should cover (tentative)

- The hexagonal architecture boundary: what "core" vs. "wire" means (ADR 0009, 0017)
- The inbox pipeline: how an incoming ActivityPub message flows from HTTP delivery to BT execution (ADR 0020, 0021, 0022)
- The outbox and delivery model (ADR 0042, 0066)
- The BT orchestration model: how behavior trees drive state transitions
- Ports and call-out points: where an implementer plugs in their own logic (ADR 0025)
- What the reference implementation provides vs. what an implementer must supply

## Open questions to resolve before scoping

1. Audience: a developer building a *compatible* system (needs the protocol contract), or a developer *contributing* to the reference implementation (covered better by #604)?
2. Diataxis quadrant: Explanation (conceptual) or How-to (task-oriented)?
3. Relationship to `reference/specs/architecture.md` — does this page supplement the auto-rendered specs or replace the need for a prose version?
