# Vultron Project — September 2026 Work Sponsor Report

## Executive Summary

September 2026 merged 358 pull requests and closed 642 issues, a pace on par with August. The month's defining change was structural: the reference implementation's two parallel object models (one for internal domain logic, one for the wire-format messages actors exchange) were collapsed into a single model, removing a long-standing source of translation bugs. Around that core change, the inbound message pipeline was hardened so that malformed, untrusted, or misrouted messages are refused with a named reason instead of partially applied; the rules for who holds authority over a case and how embargo consent works were settled in nine architectural decision records and implemented; message delivery between actors was made ordered and byte-faithful; and the public documentation site was rebuilt around a modular protocol specification with a reader-level information architecture. Several decisions recorded this month are not yet fully implemented, and those are flagged below.

---

## One Object Model: The Wire Format Is Now a Serialization, Not a Second Hierarchy

Until September, the reference implementation kept two class hierarchies for the same concepts: a domain model used by the protocol logic, and a parallel set of wire-format classes (ActivityStreams 2.0, the standard social-web message format Vultron uses between actors), with translators converting in each direction. Every field added to one side had to be mirrored on the other, and a translator that lagged behind produced silent data loss. Architectural decision record ADR-0099 decided that the domain model is the only model and the wire format is simply how it is serialized ([PR #3468](https://github.com/CERTCC/Vultron/pull/3468)).

The migration landed in stages over the month:

- **The wire/core boundary was frozen first.** Reference-field sets are now derived from type annotations rather than hand-maintained lists, the JSON-LD context document is generated from the classes, and domain objects refuse unknown fields rather than silently keeping them ([PR #3531](https://github.com/CERTCC/Vultron/pull/3531)).
- **All 27 paired wire classes were deleted** and replaced with aliases onto the domain classes, so existing import sites kept working while the duplicate model went away ([PR #3540](https://github.com/CERTCC/Vultron/pull/3540)). Follow-up work removed the remaining alias shims and dead conversion branches ([PR #3679](https://github.com/CERTCC/Vultron/pull/3679), [PR #3755](https://github.com/CERTCC/Vultron/pull/3755)).
- **Rendering goes through one port.** Every place the core produces wire-format output now goes through a single rendering port, and an automated architecture check (a ratchet test, which prevents a design boundary from eroding) confirms no direct dumps remain ([PR #3676](https://github.com/CERTCC/Vultron/pull/3676), [PR #3954](https://github.com/CERTCC/Vultron/pull/3954)).
- **Persistence keys match the wire.** Stored records now use the same identity field names as the wire format, so a stored object reads back equal to what was sent ([PR #3781](https://github.com/CERTCC/Vultron/pull/3781)).
- **The specification was brought in step.** Two earlier decision records that described the two-hierarchy design were retired, eleven architecture requirements were rewritten, and ADR-0099 was graduated from provisional to accepted ([PR #3847](https://github.com/CERTCC/Vultron/pull/3847), [PR #3783](https://github.com/CERTCC/Vultron/pull/3783), [PR #3898](https://github.com/CERTCC/Vultron/pull/3898)).

A type-registry bug surfaced along the way, where the lookup table of wire types was keyed by class name instead of by the emitted type value, was fixed in the same effort ([PR #3569](https://github.com/CERTCC/Vultron/pull/3569)).

## Inbound Messages Are Judged at the Edge and Refused With a Reason

A series of fixes tightened what happens when an actor receives a message, so that a bad or untrusted message is refused before it changes any state, and the sender learns why.

- **Trust on first contact.** An actor that receives an announcement of a case it has never heard of now refuses it unless a locally derived trust anchor exists, such as a prior invitation from the same case manager. Previously such an announcement could seed a case replica from an unverified sender ([PR #3303](https://github.com/CERTCC/Vultron/pull/3303)).
- **No partial writes on refusal.** Received-side handlers now resolve which local actor the message is for before writing anything, so a refused message no longer leaves behind orphaned report or offer records ([PR #3751](https://github.com/CERTCC/Vultron/pull/3751)).
- **Role-gated effects.** The suggest-actor and accept-invitation handlers now act only when the receiver holds the case-manager role. A participant that merely holds a copy of the message no longer forwards, accepts, or admits on its own behalf ([PR #3837](https://github.com/CERTCC/Vultron/pull/3837)).
- **Handlers report a real verdict.** Before this month, "did not raise an exception" was the only success signal from a received-message handler. Handlers now return a typed result of applied, skipped, deferred, or refused, and a refusal reaches the inbox outcome with a failure reason ([PR #3704](https://github.com/CERTCC/Vultron/pull/3704), [PR #3776](https://github.com/CERTCC/Vultron/pull/3776)).
- **Unknown and malformed fields.** The parser now applies one rule to unknown keys at every depth: a near miss of a known field name (a case or separator variant, or a retired name) refuses the whole message naming every offending key, while a genuinely foreign key is set aside and logged ([PR #3951](https://github.com/CERTCC/Vultron/pull/3951)). Nested objects that fail validation are refused rather than silently downgraded to a weaker type ([PR #3233](https://github.com/CERTCC/Vultron/pull/3233)), and blank identifiers are refused in both wire and core reference fields ([PR #3899](https://github.com/CERTCC/Vultron/pull/3899)).
- **Timestamps are carried, never minted.** A receiver no longer stamps its own clock onto an object's time; the time arrives as sent or stays absent (ADR-0103, [PR #3575](https://github.com/CERTCC/Vultron/pull/3575)). Naive datetimes are normalized to UTC at the wire edge ([PR #3213](https://github.com/CERTCC/Vultron/pull/3213)).
- **Record what arrived before judging it.** Every received-message tree now begins with an intake stage that archives the message exactly as received, before any guard runs (ADR-0111, [PR #3941](https://github.com/CERTCC/Vultron/pull/3941), [PR #3761](https://github.com/CERTCC/Vultron/pull/3761)).

These changes address the specific gaps named; they do not amount to a full security review of the inbound path.

## Authority, Embargo Consent, and Case State Rules Were Settled

Nine architectural decision records this month resolved ambiguities in the protocol's governance rules, and most were implemented in the same period.

**Authority is a role, not an address.** ADR-0088 established that authority over a case belongs to whichever participant holds the case-manager role, not to a particular actor name, URL, or hosting arrangement. The code had been deciding authority four different ways, three of them by the wrong signal. A single neutral resolver replaced them, the wrong signals were deleted, and specification and documentation prose were swept to match ([PR #3219](https://github.com/CERTCC/Vultron/pull/3219), [PR #3253](https://github.com/CERTCC/Vultron/pull/3253), [PR #3290](https://github.com/CERTCC/Vultron/pull/3290), [PR #3361](https://github.com/CERTCC/Vultron/pull/3361)). Case creation now registers both the case-owner and case-manager roles so the manager role is never unfilled ([PR #3349](https://github.com/CERTCC/Vultron/pull/3349)).

**One writer for participant status.** ADR-0089 made a single automation node the only place that writes a participant's status, and moved pre-case report-handling state onto the report-to-case link where it belongs ([PR #3245](https://github.com/CERTCC/Vultron/pull/3245), [PR #3269](https://github.com/CERTCC/Vultron/pull/3269), [PR #3283](https://github.com/CERTCC/Vultron/pull/3283)).

**Embargo consent is per embargo.** The per-participant embargo-consent state machine was corrected in three steps. Its initial state was renamed from "no embargo" to "unbound" to stop it being confused with the embargo's own state (ADR-0091, [PR #3343](https://github.com/CERTCC/Vultron/pull/3343)). A signatory can now withdraw consent, which had no legal transition before (ADR-0093, [PR #3375](https://github.com/CERTCC/Vultron/pull/3375)). And a revision proposal no longer changes anyone's consent: consent is re-evaluated only when the case owner activates a revision, a shorter one carries every signatory over, a longer one lapses those who have not accepted, and terminating an embargo decides every open proposal at once ([PR #4002](https://github.com/CERTCC/Vultron/pull/4002)).

**A protocol default embargo replaces the pre-case phase.** ADR-0096 introduced a bounded, configurable default embargo (72 hours to 5 days) in place of a silent 90-day fallback, and clamped every RSVP deadline to its embargo's end ([PR #3756](https://github.com/CERTCC/Vultron/pull/3756)). A reporter's proposed embargo on the initial report now carries through to case creation ([PR #3850](https://github.com/CERTCC/Vultron/pull/3850)). ADR-0100 removed the notion of a multi-candidate embargo poll: open proposals resolve earliest-expiring first ([PR #3841](https://github.com/CERTCC/Vultron/pull/3841)).

**Case state entailments and closure.** The rule that a fix cannot be deployed before it is ready, and its sibling rules linking vendor awareness, fix state, and public disclosure, are now enforced on the received-status path and on the path where a replica applies ledger entries, not only on the local trigger path ([PR #2981](https://github.com/CERTCC/Vultron/pull/2981), [PR #3010](https://github.com/CERTCC/Vultron/pull/3010), [PR #3112](https://github.com/CERTCC/Vultron/pull/3112)). A combined three-flag state type was removed in favor of independent fix-readiness and deployment dimensions ([PR #3174](https://github.com/CERTCC/Vultron/pull/3174)). ADR-0085 made owner-close a hard boundary: an owner cannot close a case while an embargo is live ([PR #3210](https://github.com/CERTCC/Vultron/pull/3210)), and the case manager's own closed state is now recorded on the ledger ([PR #3407](https://github.com/CERTCC/Vultron/pull/3407)).

**Still in progress.** ADR-0113, which routes embargo revision negotiation through the case manager so that a replica enters the revise state on an inbound revision, was planned at month end ([PR #3912](https://github.com/CERTCC/Vultron/pull/3912)); the termination rule from it landed, but the relay itself has not. ADR-0105, on merging two cases that turn out to describe one vulnerability, is a decision only.

## Message Delivery Is Ordered and Byte-Faithful

Two long-running sources of multi-actor demonstration failures were traced to delivery mechanics rather than protocol logic, and fixed.

- **Case seed before fan-out, and the inbox off the event loop.** The case manager now queues the case-creation message before any ledger-entry announcements for that case, and the inbox processes messages in a worker thread instead of on the web server's event loop. Together these fixed the replica-gate timeouts in two scenarios and outbox congestion in the five-party scenario ([PR #3883](https://github.com/CERTCC/Vultron/pull/3883)).
- **Per-recipient ordered delivery.** ADR-0112 made the outbox deliver to each recipient in enqueue order with one in-flight delivery per recipient. Before this, concurrent drains could reorder a ledger fan-out, each gap provoked a reject, and each reject triggered a full replay into the same queue ([PR #3907](https://github.com/CERTCC/Vultron/pull/3907)).
- **The sealed body is what gets sent.** Every outbound message is now sealed as exact JSON text at emission, relayed byte for byte, and recorded on the case ledger (the append-only log of events for a case) as the same bytes. The previous path re-read the record from storage and re-normalized it, which could diverge from what the ledger said was sent ([PR #3923](https://github.com/CERTCC/Vultron/pull/3923)).
- **Bounded retries.** The inbox no longer re-queues protocol violations, and re-queues per message are capped ([PR #3690](https://github.com/CERTCC/Vultron/pull/3690), [PR #3692](https://github.com/CERTCC/Vultron/pull/3692)). Dead-lettered messages are correlated to their ledger entry for later inspection ([PR #3317](https://github.com/CERTCC/Vultron/pull/3317)).

On the demonstration side, scenarios now register themselves at import time, and every scenario table, the CI matrix, and the command-line sub-commands are generated from that one declaration (ADR-0098, [PR #3464](https://github.com/CERTCC/Vultron/pull/3464), [PR #3538](https://github.com/CERTCC/Vultron/pull/3538)). The demo harness gained a typed session object so that a misspelled trigger name is a type error rather than a runtime surprise ([PR #3436](https://github.com/CERTCC/Vultron/pull/3436)), and copied replica-verification loops across scenarios were consolidated into shared helpers ([PR #3905](https://github.com/CERTCC/Vultron/pull/3905), [PR #3978](https://github.com/CERTCC/Vultron/pull/3978)). These fixes removed the identified causes of the named failures; they do not rule out other intermittent failures surfacing in future runs.

## The Documentation Site Was Rebuilt Around a Modular Specification

153 of the month's pull requests touched documentation. The largest single change replaced a 1,634-line draft protocol specification with a modular specification assembled from 27 fragments, correcting nine normative errors found by checking the draft against the machine-readable requirements and the implementation ([PR #3265](https://github.com/CERTCC/Vultron/pull/3265)).

- **A front door for each kind of reader.** The site now opens by explaining what kind of thing Vultron is (a protocol, compared to email or chat protocols) and routes readers by situation ([PR #3646](https://github.com/CERTCC/Vultron/pull/3646)). Every page declares its intended reader type and prerequisite level, the navigation is ordered by level, and a build check fails if any page depends on one above its own level ([PR #3577](https://github.com/CERTCC/Vultron/pull/3577), [PR #3648](https://github.com/CERTCC/Vultron/pull/3648), [PR #3864](https://github.com/CERTCC/Vultron/pull/3864)).
- **Practitioner-facing pages.** New pages explain a case from a participant's seat and walk a CVD (coordinated vulnerability disclosure) program through adoption ([PR #3842](https://github.com/CERTCC/Vultron/pull/3842)). A conformance matrix and standards crosswalks map capability sets and external standards to governing specification sections ([PR #3849](https://github.com/CERTCC/Vultron/pull/3849)).
- **Message reference.** Consolidated reference pages for every protocol message type, with a build-time mapping table between the formal shorthand and the wire form ([PR #3099](https://github.com/CERTCC/Vultron/pull/3099), [PR #3171](https://github.com/CERTCC/Vultron/pull/3171), [PR #3279](https://github.com/CERTCC/Vultron/pull/3279)). A tested tutorial walks a developer through submitting a report, with its commands rendered from code that is itself under test ([PR #3140](https://github.com/CERTCC/Vultron/pull/3140)).
- **Build gates that actually fail.** Every site build is now strict, a link gate resolves every internal reference in the built output, a URL-continuity gate ensures that 162 URLs from the previously published site still resolve or are declared withdrawn, and a check confirms that pages claimed withheld are actually absent from the build ([PR #3731](https://github.com/CERTCC/Vultron/pull/3731), [PR #3727](https://github.com/CERTCC/Vultron/pull/3727), [PR #3573](https://github.com/CERTCC/Vultron/pull/3573)). The documentation linter now covers include fragments and runs a spell checker ([PR #3851](https://github.com/CERTCC/Vultron/pull/3851)).
- **Future work made visible.** A federation design page and a collection of ten open questions were promoted from internal notes into the public docs, each wired to a tracking issue ([PR #3341](https://github.com/CERTCC/Vultron/pull/3341), [PR #3369](https://github.com/CERTCC/Vultron/pull/3369)).

ADR-0106 decided that each machine-facing interface (wire vocabulary, trigger API, ledger format) is versioned independently of the release tag; the first implementation step landed, and the trigger API's OpenAPI contract is now frozen in a golden snapshot ([PR #3976](https://github.com/CERTCC/Vultron/pull/3976)).

## Engineering Discipline and Tooling

- **Plan before build.** 84 pull requests this month were written plans for a single issue, reviewed and merged before implementation began. A new completeness doctrine separates filing a follow-up from deferring work, and makes fixing now the default ([PR #3092](https://github.com/CERTCC/Vultron/pull/3092)). Pull request bodies now record whether documentation currency was checked, and triage verifies it ([PR #3939](https://github.com/CERTCC/Vultron/pull/3939)).
- **Defect-masking patterns removed.** Blanket exception handlers in the core were narrowed or deleted, with an automated check keeping them out of the automation layer ([PR #3338](https://github.com/CERTCC/Vultron/pull/3338)). A runtime guard and a static check enforce that no automation node ever reports a "running" status, which the protocol's synchronous model does not support ([PR #3244](https://github.com/CERTCC/Vultron/pull/3244)).
- **Faster commits.** Linters are skipped when their inputs are unchanged since the last success, removing roughly 105 seconds of duplicate work per commit ([PR #3154](https://github.com/CERTCC/Vultron/pull/3154)).
- **Measured planning.** Pull request size bands were recalibrated against the repository's own distribution of 692 merged PRs, replacing eight prose copies of the thresholds with one computed table ([PR #3537](https://github.com/CERTCC/Vultron/pull/3537)).
- **Decided, not yet applied.** ADR-0094 adopts the ruff linter in place of three current tools, and ADR-0104 specifies an interactive demonstration UI fed by a live case-ledger stream. Neither has implementation work yet. The trigger API simplification (ADR-0110) completed its second of several additive steps ([PR #4001](https://github.com/CERTCC/Vultron/pull/4001)).

34 automated dependency bumps were merged cleanly during the period, including updates to `uvicorn`, `pydantic`, `mypy`, `pyright`, `flake8`, and the documentation toolchain.
