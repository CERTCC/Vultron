Planned IDEA-2066 ("Embargo offers (invites) should support optional expiration
deadlines via `Offer.end_time`") into ADR-0059 plus three spec groups.

**Docs PR**: <https://github.com/CERTCC/Vultron/pull/2210>

## Three premises changed during planning

1. **It is an `Invite`, not an `Offer`.** There is no `Offer` anywhere in the
   embargo path — `em_propose_embargo_activity()` returns `as_Invite`, and
   `InviteToEmbargoOnCasePattern` matches `activity_=TAtype.INVITE`. The
   mechanism survives unchanged because `end_time` is inherited from `as_Object`
   by every activity, but the field is `Invite.end_time`.

2. **The `end_time` collision is sharper than the issue stated.** The issue
   argued the activity-level field avoids collision with `EmbargoEvent.end_time`
   "which lives on the object not the activity". In fact both live in the *same
   JSON document* one nesting level apart: `Invite.end_time` (RSVP-by) and
   `Invite.object_.end_time` (embargo expiry, on the nested `as_EmbargoEvent`).
   That is the strongest argument for the ADR and the principal implementation
   hazard.

3. **A deadline mechanism was already specified — and entirely unimplemented.**
   CM-18-002's pocket veto already defines a timer-driven `INVITED → DECLINED`
   on a configurable window (default 7 days). Nothing implements it:
   `PEC_Trigger.DECLINE` fires from exactly two sites, both explicit-`Reject`
   paths. So this idea is not a new mechanism — it makes that window explicit
   and bilateral. The plan reconciles the two rather than adding a second
   timeout notion.

## Decisions taken

- `Invite.end_time` is authoritative when present; the CM-18-002 policy window
  is the fallback, so invitations that omit it behave exactly as today.
- The CaseActor (`CVDRole.CASE_MANAGER`) enforces expiry, by **lazy evaluation**
  from `(end_time, now)` — no scheduler required. `EmbargoTimerExpired` (#1893)
  is an optional accelerator, never a prerequisite.
- A late `Accept` is **never refused** (Postel): honour it when terms are
  current, re-invite with current terms when stale, acknowledge as a no-op
  (retaining case participation) when no embargo remains.
- **No new PEC state** for "never responded". Nothing branches on the
  distinction; the provenance lives in the canonical ledger (ADR-0019), not in
  the state machine. Avoids encoding path history — consistent with ADR-0048.
- Abuse mitigation is a 72h minimum window with **clamp-on-receipt**, not
  rejection: rejecting a coercively short invite gives a hostile sender exactly
  the outcome they want.
- ADR status is `accepted-provisional`, not `accepted` — the decision is
  ratified but unimplemented, and MS-14 requires status and prose to agree.
