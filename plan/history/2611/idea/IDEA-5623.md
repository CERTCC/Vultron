Theme: theme:dev-workflow — Each Epic's title on Project #24 says what someone can do or count on when it is done, so the board reads as a list of outcomes.

## Summary

Make every Epic title answer one question: **"When this is done, what can someone do, or count on, that they can't today?"** Write the answer in domain terms, starting with who it is for: a reporter, vendor, coordinator, participant or the CASE_MANAGER for protocol work, and a maintainer, agent or docs reader for project work. Keep the mechanism, ADR numbers and spec IDs in the body.

## Motivation

A scan of the 39 open Epics in Focus, Now and Next (2026-11-02) found four title kinds. Only one of them says what the Epic is about from the board view:

| Kind | Examples | What a board reader learns |
|---|---|---|
| Outcome | #5100, #5578 | What will be true when it is done |
| How it's built | #5193 "Staged inbox: one record per message, doors in a fixed order, one role check picks the path (ADR-0153, ADR-0154)" | How it works, not why anyone cares |
| Activity | #5354, #5490, #5491 "Reconcile … spec statements with the code and with each other" | Work is happening; the three can't be told apart |
| Topic label | #1156 "Actor signing (prototype)", #676 "Interactive Demo UI", #2682 "Trigger endpoint observability contract" | The area, not what you get |

The better sentence often exists already. Every Epic's `Design idea:` line is usually clearer than its title. For #2682 it is: "A trigger's caller can see what the protocol actually did, including a refusal or an internal error."

An outcome test fits better than a "new features" test. About half these Epics deliver a guarantee or remove a class of defect, not a feature (#3329, #5396, #5410, the reconcile Epics). A feature test would push those toward vague titles or invented capabilities.

Side effect: outcome titles expose likely overlaps. #3329 (fail-loud code) and #5408 (fail-loud lint) look like one outcome. #5354, #5490 and #5491 differ only in which spec groups they cover. Retitling forces either a merge or a clear statement of what separates them.

## Rough Approach

1. **The title rule.** Start with the audience, in domain roles. Keep mechanism, ADR numbers and spec IDs out. Make the opening words tell the Epic apart from its siblings. Default the title to a shortened form of the design idea.
2. **Put the rule where Epics are made:** `create-epic`, `calve-epics` and the PAD-02 Epic rules.
3. **Add a check to the theme checker.** Flag Epic titles that carry bare IDs, run too long, or don't match the opening of the design idea.
4. **Remove a duplicate line.** Epic bodies repeat the design idea in both the `Theme:` line and the `Design idea:` line. Once the title states the outcome, one of these can go.
5. **One-time retitle.** Propose new titles for every open Epic as a table in the same PR, and have a human review them before any board change.

Example rewrites from the scan:

| # | Today | Outcome title |
|---|---|---|
| 5193 | Staged inbox: one record per message, doors in a fixed order… | A re-delivered message never repeats its effects |
| 1156 | Actor signing (prototype) | Participants can verify who sent each message (prototype keys) |
| 2682 | Trigger endpoint observability contract | Trigger callers can see whether their action succeeded, was refused, or failed |
| 5090 | ActivityPub read surface: dereferenceable objects… | Peers can fetch any case object, actor or collection by its URL |
| 3188 | Protocol asks: durable ask objects with deadlines… | Requests to participants carry deadlines and get followed up |
| 5396 | Arrival-order independence: … (SYNC-19) | Messages produce the same case outcome in any arrival order |
| 3329 | Fail-loud defensive code: narrow catches… | Internal errors surface; they never pass as success or refusal |
| 1160 | Failure and abnormal flow demo scenarios | Demos show silent participants, coordination breakdown and early disclosure |
| 5354 | Reconcile case-management, messaging… spec statements… | Case-management and messaging specs say what the code does |
| 3708 | Project #24 two-path board: Epic-only Schedule… | The board shows what matters now and which PRs need me |
