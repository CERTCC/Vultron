# UCORG-05-011 (retired)

- **Retired**: 2026-11-05 (#5858)
- **Replacement**: IO-01-006
- **Why**: It restates IO-01-006, which already derives InboxOutcome.status from the handler disposition with the same four-way mapping; IO-01-007 already carries the REFUSED reason into failure_reason. The InboxOutcome model belongs to the IO spec.
- **Last text**:

```yaml
  - id: UCORG-05-011
    priority: MUST
    kind: project
    verification_debt: '#2575'
    statement: >-
      When a dispatch occurred, this codebase MUST derive `InboxOutcome.status` from the
      handler's `HandlerDisposition`. It does not infer the status from the absence of a
      raised exception. Under this rule, `APPLIED` and `SKIPPED` map to `processed`, and
      `DEFERRED` maps to `deferred`. Also, `REFUSED` maps to `rejected`, with
      `failure_reason` taken from the handler's `reason`.
    rationale: >-
      If the outcome comes from "dispatch did not raise", a handler that takes no action
      is still reported as `processed`. Three components produce `deferred`, and they
      must not be confused. `DeferCheckNode` defers before dispatch for missing case
      context. `DereferenceCheckNode` defers before dispatch while an object is fetched
      (AKM-05-010). A handler returns `DEFERRED` after dispatch for an entry that waits
      for its predecessor. All three reach the same `InboxOutcome.status`, but only the
      last goes through this mapping.
    adr:
    - ADR-0095
```
