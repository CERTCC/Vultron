# CM-11-005 (retired)

- **Retired**: 2026-10 (audit of unsupervised decisions, #4195)
- **Why**: the ID was reused with the opposite force. Until 2026-10-01 it required an invited
  actor to obtain its `VultronOfferRecord` from the ledger backfill so the standard
  `validate-report` trigger could run (ADR-0070 as first accepted). The #4006 rewrite replaced
  it with `MUST NOT` answer the original report Offer, under the same ID, so every citation of
  the old rule silently pointed at its opposite. The old rule was retired with its decision
  (ADR-0070 superseded by ADR-0121). The new rule carries a new ID, CM-11-018.
- **Last text of the original rule** (as of 2026-09-30):

```yaml
  - id: CM-11-005
    priority: MUST
    kind: architecture
    statement: >-
      An invited actor MUST obtain its `VultronOfferRecord` for the case's vulnerability
      report by processing the `add_report_to_case` `CaseLedgerEntry` backfilled from the
      CASE_MANAGER — not by any form of synthetic injection or out-of-band seeding. The
      `add_report_to_case` ledger entry embeds the full `VulnerabilityReport` and the
      original offer metadata; processing it creates both the `VulnerabilityReport` replica
      and the `VultronOfferRecord` in the invited actor's DataLayer, enabling the standard
      `validate-report` trigger to proceed without modification.
    rationale: >-
      Three options were evaluated when CONCERN-2320 was filed: (1) reuse `validate-report`
      with the `VultronOfferRecord` obtained from the ledger backfill, (2) add a separate
      `engage-case`/`validate-case` trigger that advances RM without an OfferRecord, and
      (3) exempt invited actors from the RM.VALID step entirely. Option 1 was chosen because
      it preserves protocol uniformity (all participants run the same triage cycle), avoids
      forking the RM state-machine path, and is already fully supported by the
      `add_report_to_case` ledger backfill mechanism. See ADR-0070.
    verification: Inspection of `vultron/core/` confirms that the `add_report_to_case`
      ledger-backfill path creates both the `VulnerabilityReport` replica and the
      `VultronOfferRecord`, enabling the standard `validate-report` trigger without synthetic
      injection.
    note: >-
      This requirement supersedes the prior `seed-offer-record` demo-only scaffold
      (`vultron/adapters/driving/fastapi/routers/demo_triggers.py`), which was introduced
      as a temporary workaround before the ledger backfill mechanism existed. That endpoint
      MUST be removed; see TRIG-02-006 and the tracking issue created when CONCERN-2320
      was resolved.
    relationships:
    - rel_type: depends_on
      spec_id: CM-11-002
    - rel_type: implements
      spec_id: CM-11-002
    adr:
    - ADR-0070
```
