# RSH-05-021 (retired)

- **Retired**: 2026-10-20 (#3741)
- **Replacement**: RSH-09-006
- **Why**: ADR-0107 detail 5: a received status is accepted whole or refused whole, so the ledger never records a status nobody sent (#4451 decision on #3741). The replica-apply fault rule is unchanged; it moved out of the retired group.
- **Last text**:

```yaml
  - id: RSH-05-021
    priority: MUST
    kind: protocol
    verification: >-
      `test/core/behaviors/sync/test_announce_tree.py::TestAnnounceTreeEmitImpossibleStateFault::test_impossible_composite_state_emits_fault_and_blocks_persist`
      confirms an entailment violation blocks the status update and emits
      `Create(ProcessingFault)` to the CASE_MANAGER.
    statement: >-
      When applying an `Announce(CaseLedgerEntry)` whose entry adds a participant status, a
      receiver MUST evaluate the composite-state entailments (RM↔VF and RM↔D per CSB-18-001,
      VF↔D per CSB-17-001) against the effective participant state from the entry. If any
      entailment is violated the receiver MUST NOT apply the status update, and MUST send
      `Create(ProcessingFault)` with failure class `StatusAssertionRefused/ImpossibleState`
      to the CASE_MANAGER.
    rationale: >
      A CASE_MANAGER that is buggy or hostile can commit an entry whose participant
      state violates `composite_state_violations()` — the same entailment set
      the emit and receive paths already enforce. Without this check, every
      replica silently adopts an impossible combination: the same actor would
      have refused to *emit* the value, yet accepts it when the CASE_MANAGER
      broadcasts it. Silence is the specific problem: the contradiction is
      only discoverable by reading devlogs.
      Using `Create(ProcessingFault)` rather than `Reject(CaseLedgerEntry)`
      avoids triggering a CASE_MANAGER replay loop — the committed entry cannot
      be uncommitted, so replaying it would produce the same refusal
      indefinitely. `ProcessingFault` is the right signal for semantic
      invalidity (ASK-07-001). The failure class
      `StatusAssertionRefused/ImpossibleState` is a URI sub-path of
      `StatusAssertionRefused`, so a consumer that understands the parent class
      recognises this as a narrower form of the same fault.
      The tree-structural guarantee (rather than node-level fault emission) keeps
      the apply node a pure domain check (returns FAILURE on violation) and
      the emission a composable side-effect, consistent with protocol-significant
      behavior living in the tree (BTND-01).
    note: >
      `composite_state_violations()` in `vultron/core/states/composite_state_invariants.py`
      is the shared evaluator; both the emit path
      (`ValidateTriggerTransitionsNode._validate_entailments`) and the receive
      path (`_adjudicate_composite_state_entailments`) already call it.
      The tree change wraps the inner Sequence in a Selector whose fallback
      node emits `Create(ProcessingFault)` and then returns FAILURE, so the
      overall Sequence still fails and `PersistReceivedLogEntry` is blocked
      (SYNC-12-001 is preserved).
      The failure class constant
      `VULTRON_FAILURE_STATUS_ASSERTION_REFUSED_IMPOSSIBLE_STATE` lives in
      `vultron/core/models/fault_classes.py` alongside
      `VULTRON_FAILURE_STATUS_ASSERTION_REFUSED`.
      The check reads the entry's status as carried; a replica carries none of
      its own values over it (CM-23-016).
    relationships:
    - rel_type: refines
      spec_id: RSH-05-001
    lint_suppress:
    - missing_story_reference
```
