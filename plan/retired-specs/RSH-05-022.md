# RSH-05-022 (retired)

- **Retired**: 2026-10-20 (#3741)
- **Replacement**: RSH-09-008
- **Why**: ADR-0107 detail 5: a received status is accepted whole or refused whole, so the ledger never records a status nobody sent (#4451 decision on #3741). The refused-outcome rule is unchanged in substance; it moved out of the retired group.
- **Last text**:

```yaml
  - id: RSH-05-022
    priority: MUST
    kind: project
    statement: >
      When `FilterParticipantStatusDimensionsNode` returns `FAILURE` for an
      `Add(ParticipantStatus, CaseParticipant)` (i.e. the assertion is wholly
      refused because the filtered status is indistinguishable from the
      participant's current state), the inbox processing pipeline MUST surface
      this as a `rejected` `InboxOutcome` rather than `202 Accepted / processed`.
      Senders MUST be able to distinguish total refusal (`rejected`) from
      partial accept (`processed`).
    rationale: >
      Before ISSUE-3199, a wholly-refused status assertion silently returned
      `202 Accepted / processed` because `AddParticipantStatusToParticipantReceivedUseCase.execute()`
      did not raise on BT FAILURE, so the inbox `DispatchNode` saw no exception
      and wrote `"processed"` to `KEY_OUTCOME_STATUS`. Senders had no way to
      distinguish a fully-refused assertion from one that was partially accepted.
      This is the sender-feedback diagnostic gap identified in ISSUE-2255.
    verification: >
      Unit tests confirm that `AddParticipantStatusToParticipantReceivedUseCase.execute()`
      returns `HandlerResult.refused` when `FilterParticipantStatusDimensionsNode`
      returns FAILURE, which `DispatchNode` maps to a `rejected` `InboxOutcome`
      (HP-01-003, ADR-0095).
    note: >
      A withheld adoption at `StatusAdoptionGate` does NOT produce `rejected`:
      the claim is recorded on the participant and only its adoption as
      canonical is withheld, which is not a refusal of the assertion content,
      so the handler returns `SKIPPED` and emits no fault. A sender that is not
      a case participant is refused like any other untrusted sender
      (HP-01-003). `_filter_node_wholly_refused()` and `_adoption_gate_blocked()`
      in `vultron/core/use_cases/received/status.py` tell these cases apart by
      walking the tree after execution.
    relationships:
    - rel_type: extends
      spec_id: RSH-05-005
```
