Issue #2906 (filed by pre-PR code review on #2490) reported that
`_adjudicate_vf` skips its monotone-forward check when `current_vf is None`, and
concluded a peer could "assert `CS_vf.VF` directly, skipping the vf→Vf→VF
ladder."

The code observation was correct. The **cause** was not, in two ways:

1. Skipping ladder rungs is deliberate on the received path. CSB-16-001's
   rationale scopes strict adjacency to local write nodes; RSH-05-019 and
   RSH-06-001 say the same for PXA and RM. A peer may advance several steps
   between status messages.
2. Reading `None` as the baseline `CS_vf.vf` would have refused *nothing*:
   every value is a monotone advance on the bottom of the ladder. The
   "fix" the issue asked for was a behavioural no-op. Worse, treating absence
   as an initial state contradicts ADR-0075 (a non-VENDOR participant has no
   vendor path) and would have broken a test that already pins that semantics.

The real defect was adjacent: no cross-machine entailment check on the receive
path, so `vf=VF` was accepted alongside a pre-acceptance `rm`. That refuses the
reporter's scenario for a different reason.

**Lesson for the bugfix skill's Phase 2b/2c:** when a bug report supplies a
cause, treat it as a hypothesis to falsify, not a starting point to implement.
The cheapest falsification here was to evaluate the proposed predicate by hand
against the enum values (`is_monotonic_vf_forward(vf, VF) is True`) and to grep
the spec corpus for whether the check the report wants is already scoped away.
Both took minutes and would have been skipped by going straight to the patch.

**Second-order lesson:** a bug report generated by code review of a *different*
PR carries no more authority than the reviewer's local context. #2906's body
even says "exists on origin/main, not introduced by #2490" — an accurate
provenance note that says nothing about whether the diagnosis is right.
